## 2. 根 registry

### 2.1 根标识与数据模型

**identity 三层**（按用户 2026-10-26 通用性缺口第 1 条）：

1. `canonicalRoot`：绝对路径归一 —— `realpath`（存在时）+ Windows 盘符大写 + UNC 归一（`\\?\UNC\srv\share` → `\\srv\share`，`\\?\C:\` → `C:\`）+ 去尾分隔符 + 合并 `\\?\` 长路径前缀。
2. `rootId`：**路径 hash**，`sha256(platformFold(canonicalRoot)).slice(0,16)`（16 hex = 64 bit；Windows 下 `platformFold` = 小写，POSIX 原样）。它是**根的唯一标识**：state 的键、审计字段、账本聚合键、status 的 id 都用它。
   - 碰撞处理：若算出的 `rootId` 已存在且对应**不同** `canonicalRoot` → 前缀长度 16→20→24 重算（注入 hash 函数可测），root audit `root-id-collision`；**绝不合并两个不同根**。
3. `name` / `project`：`name = basename(canonicalRoot)`；`project` 默认 = `name`（允许配置根用 `config.project` 覆盖）。**两者都只做展示**——不同路径同名（如两个 `tools`）靠 `rootId` 区分，账本/记忆/审计不得只按 `project` 聚合。

**条目（entry）**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `rootId` | string（16–24 hex） | 路径 hash = 根标识；state 键 |
| `root` | string（绝对路径） | `canonicalRoot`（展示/落盘/复核 hash） |
| `name` | string | `basename(root)`，展示名 |
| `project` | string | 展示用项目名（默认 `name`；配置根可覆盖） |
| `origin` | `'inferred' \| 'config'` | 第一次进入 registry 的来源 |
| `inferredAt` | string \| null | 首次推断时间；config 来源为 null |
| `inferredFromCwd` | string \| null | 首次推断时的会话 cwd |
| `firstSeenAt` | string | 第一次登记时间 |
| `lastSeenAt` | string | 最近一次有会话命中（写盘节流，见 §2.4） |
| `state` | `'active' \| 'fail-closed'` | 落盘的纳管状态；`active` 不等于“本进程有会话”（运行期 active/idle 见下） |
| `failClosedReason` | string \| null | `memory-root-absolute` / `memory-root-escape` / `memory-root-not-fixed` / `memory-root-symlink-escape` |

> 不持久化会话列表（隐私 + churn）；会话→根映射只活在进程内。
> 运行期的三态：`active`（本进程有会话，P2 起 store 已打开）、`idle`（state 里有、本进程无会话，不建 store）、`fail-closed`（containment 拒绝）。

### 2.2 生命周期（不扫描磁盘）

```
apply()
  ├─ identity = resolvePersistenceIdentity(ctx)          // 不变
  ├─ rootAudit = createRootAudit(identity)              // 用户级，apply 即建文件
  ├─ state = loadStateV2(stateFile)                     // 读 v2 / 迁移 v1 / 损坏处理
  ├─ registry = new RootRegistry({state, rootAudit, configRoot, home})
  ├─ attachRootId = configRoot ? idOf(configRoot) : state.primaryRootId
  ├─ attachRootId != null → startRuntime(该根)          // 与今天同路径
  └─ attachRootId == null → 等首个会话事件推断 → 登记 + primary → startRuntime
session/event(session)
  ├─ registry.resolveSessionRoot(session)
  │    ├─ 已 pin → 返回（cwd 不一致 → root-drift，不换根）
  │    ├─ 子会话且有父 pin → 继承父根（source=parent）
  │    ├─ cwd 空/无 .git 祖先 → status:'no-root'        // 3A，完全不碰
  │    ├─ 命中 config 根 → source='config'
  │    ├─ 已在 state → source='persisted'
  │    └─ 新根 → 登记 + 写 state + root audit('root-registered')
  └─ status:
       'managed'     → 今天的行为（P1 只有 primaryRoot）
       'unmanaged'   → 跳过（P1；P2 起改为 managed）
       'no-root'     → 跳过（3A）
```

- **根集合的唯一来源是 `session/event`**：不 readdir、不枚举盘符/工作区、不启动扫描；`apply` 时只读 state 文件（用户级），不碰任何工作区。
- 状态里的 roots 是“**曾出现根**”（持久化并集）；本进程的“**纳管根集合**”= 本进程出现过会话的根，P2 起按需懒开 store。`/cg status` 两者都显示（§4.4）。
- 子会话不因自己的偶发 cwd 新增根：父根已知时继承父根；父根未知才按自己的 cwd 推断。**待确认**（见 §8-6）。

### 2.3 会话→根算法（伪代码）

```
resolveSessionRoot(session):
  sid = session.header.id ?? session.id ?? null
  isSubagent = session.header.origin === 'subagent' || session.header.parentSession !== undefined
  cwd = sessionCwd(session)                      // header.cwd 优先，退回 session.cwd
  if sid != null and pin.has(sid):
     pinned = pin.get(sid)
     if cwd != '' and !cwdWithinRoot(cwd, pinned.root):
        drift(sid, pinned.root, cwd)             // 只诊断，不换根
     return pinned
  if isSubagent and session.header.parentSession pinned:
     return pinInherited(sid, parentPin)         // 根继承；不新增条目
  if cwd == '': return { status:'no-root', reason:'cwd-missing' }
  root = (configRoot != null && cwdWithinRoot(cwd, configRoot))
           ? configRoot                          // 显式配置仅作优先匹配根（需求 :460）
           : inferRootFromCwd(cwd, {exclude: identity.home ?? identity.dir})
  if root == null: return { status:'no-root', reason:'no-git-ancestor' }
  entry = ensureRoot(root, {cwd})                // 已存在→lastSeenAt；新的→登记+写 state
  if sid != null: pin.set(sid, entry)            // 首个可判定事件定根
  return { status: isManaged(entry) ? 'managed' : 'unmanaged', entry, source, isSubagent }
```

- `pin` 上限 1000 条 LRU；无 `sid` 的会话不 pin（每事件现算，cwd 稳定时结果一致）。
- **cwd 为空 → `no-root`（fail-closed）**，但子会话先走父根继承。已按需求 `:474` 确认；B 下“未知会话写进主根记忆”的风险由此关闭。
- `root-drift` 写**pinned 根**的 per-root audit（managed 时）；unmanaged 只 logger。

### 2.4 根发现的加固（worktree / 符号链接 / UNC / 盘符）

| 场景 | 规则 |
|---|---|
| `.git` 是**文件**（worktree/submodule） | 用 `existsSync` 判存在，不要求目录（现 `inferRootFromCwd` 已是如此，补测试） |
| cwd 是**符号链接/junction** | 先 `realpath(cwd)` 再上溯；最终 `canonicalRoot` 也 realpath；junction 循环用 64 层上限兜底 |
| 根内某级是 junction 指向盘外 | `canonicalRoot` 取 realpath 后的真实路径；不把链接路径当根 |
| **UNC** 路径 | `path.resolve` + 前缀归一：`\\?\UNC\srv\share\...` → `\\srv\share\...`；`\\?\C:\...` → `C:\...`；`isAbsolute` 对 UNC 为真；rootId 用归一后的串；**可判根（存在且可 realpath）则纳管，不可判 → `no-root`（3A）** |
| **盘符大小写** | realpath 后盘符大写；`platformFold` 再统一小写算 hash/比较；同根不同写法只产生一个 rootId |
| 相对路径/空 cwd | 不猜；`no-root`（3A） |
| 根不存在（会话 cwd 已删） | 不登记（`inferRootFromCwd` 返回 null）；不建目录 |

### 2.5 持久化、并发、节流、限额

- **读**：`loadStateV2(stateFile)`；v1 文件 → 先迁移（§3.3）；损坏 → 见 §3.2。
- **首次推断（无 state 文件）**：沿用 v1 的 `tmp + link` **独占发布**（`root-state.js:178-210`）：两进程同时首推，只有一方建文件，另一方读回既有 `primaryRootId`。
- **后续写入（文件已存在）**：`read-merge-write` —— 读当前 v2 → 按 `rootId` 合并（新条目 union；`lastSeenAt` 取 max；`state` 一旦 fail-closed 不被普通登记覆盖）→ 原子 `tmp+rename`。两进程同时加不同根 = 两个条目都留下；同时加同根 = rootId 相同、内容等价。
- **写盘节流**：`lastSeenAt` 内存里实时更新，落盘条件 = ①新根 ②fail-closed ③迁移 ④距上次落盘 >1h。
- **失败**：state 写失败 → 内存继续（状态只在本次进程有效）、`rootAudit('root-state-write-failed')`、`/cg status` 显式 `state-write-failed`；**不抛错**。
- **根限额（用户拍 A）**：**不设硬上限**；`ROOT_WARN_THRESHOLD=16`，注册后 `count > 16` 时写一次 `root-limit-warn`（含 `rootCount`）+ warn + status 提示；**照常登记，绝不拒绝**。P2 再谈 idle 根归档（仍然不是拒绝）。

### 2.6 API 形状（`src/roots/registry.js`）

| 成员 | 返回 | 说明 |
|---|---|---|
| `static load({stateFile, rootAudit, configRoot, home, now, logger, hash})` | `RootRegistry` | 读/迁移/损坏处理 + 建对象 |
| `resolveSessionRoot(session)` | `{status, entry, source, reason?, drift?, isSubagent}` | 唯一会话判定入口；`status ∈ managed\|unmanaged\|no-root`；`source ∈ config\|persisted\|inferred\|parent` |

| `list()` | `entry[]` | 只读快照（按 rootId 排序） |

## 3. 状态文件 v2 + v1 迁移

### 3.1 schema

```jsonc
{
  "version": 2,                 // 必填，严格 === 2
  "profile": "desktop",         // 可空；身份名（诊断）
  "roots": { "<rootId>": { ...entry... } },   // 必填，对象；键 = 路径 hash
  "primaryRootId": "3f2a…",     // 可空；P1 过渡字段
  "primaryRoot": "D:\\...",     // 可空；展示路径（与 primaryRootId 对应）
  "configRoot": "D:\\...",      // 可空；v1 镜像语义保留（只审计，不参与选择）
  "migratedFrom": 1,            // 可选；仅迁移时写
  "migratedAt": "ISO"           // 可选；仅迁移时写
}
```

**读取校验**（不抛错，坏 → `null` 或逐项拒绝）：

- 顶层必须是对象、`version===2`、`roots` 是对象；未知字段**容忍**（向前兼容）。
- 条目坏值（`root` 非绝对/空、`origin` 非法、`state` 非枚举、时间非字符串）→ **该条目丢弃**（其余保留），`rootAudit('root-entry-invalid', {reason})`；不因一条坏数据让整文件失效。
- **rootId 必须由 `root` 重算并相等**：不等 → 丢弃该条目 + `root-entry-invalid`（防手工改键指向别处）；不信任文件里的键。
- `primaryRootId` 不在 `roots` 里 → 视为 `null` + audit（P1 回落到等待推断）；`primaryRoot` 与条目 `root` 不一致 → 同样丢弃 primary（以 rootId 为准）。

### 3.2 损坏 / 版本不符

| 读到 | 动作 |
|---|---|
| 文件不存在 | 正常：等首推 |
| JSON 解析失败 / 顶层类型错 / `roots` 不是对象 | **不覆盖**：同目录 rename 为 `root-state-<p>.corrupt-<UTC>.json`，root audit `root-state-corrupt`，按“无 state”启动 |
| `version===1` | 迁移（§3.3） |
| `version===2` | 正常加载 |
| `version > 2`（未来格式） | **不改名、不覆盖、本次进程不写 state**（防降级写坏未来数据）；按“无 state”启动 + root audit `root-state-unsupported-version`；P1 只有 config 根能挂，否则等推断（仅内存） |

> 损坏文件**只 rename 不删除**（用户级目录，属允许写入位置；不碰任何项目文件）。

### 3.3 v1 → v2 迁移（一次性、幂等）

1. 读 v1，按现有 `readRootState()` 校验（`version:1` + `root` 绝对 + `inferredFromCwd/configRoot/instance` 可选）。
2. 备份：`copyFile(stateFile, root-state-<p>.v1.bak)`（已存在 `.v1.bak` 则加时间戳，不覆盖旧备份）。
3. 构造 v2：
   - `id = rootIdOf(v1.root)`；`roots[id] = {rootId:id, root, name:basename(root), project:basename(root), origin:'inferred', inferredAt, inferredFromCwd, firstSeenAt: inferredAt ?? now, lastSeenAt: now, state:'active', failClosedReason:null}`
   - `primaryRootId = id`；`primaryRoot = v1.root`
   - `configRoot = v1.configRoot ?? null`
   - `migratedFrom:1, migratedAt:now`
4. 原子写（`tmp+rename`）+ root audit `root-migrated {fromVersion:1,toVersion:2,rootId,root,path,backupPath,rootCount:1}`。
5. **幂等**：已是 v2 → 直接返回，不备份、不重写；迁移中途崩溃 → 文件仍是 v1（rename 原子）→ 下次重迁。
6. 迁移**不改变**任何项目文件、不创建根内文件（只读 v1 的用户级文件）。

**v1 代码回滚警告**：v1 的 `readRootState()` 只认 `version===1`，会读不出 v2 → 首次推断时 `persistInferredRoot` 遇 EEXIST 读回 null → `writeRootState` **覆盖 v2**。所以：**回滚到 v1 代码前，先把 `.v1.bak` 恢复成 `root-state-<p>.json`**；否则根 registry 丢失。P1 期间桌面不装新代码，风险只在开发机测试目录。

### 3.4 与“根不得静默改变”的关系

- 重启后：`primaryRootId` 从 v2 读回，不再重新推断 → 不静默变根。
- 首推时两进程竞争：`link` 独占，输方读回赢方的主根。
- `configRoot` 增删仍按 v1 语义写 `project-root-changed`（移到 root audit，见 §4）。
- 记忆不迁移、不删除（R-MEMROOT 第 5 条）。
- 卸载：保留各根 `memory/governance/`（P4 Runbook 写明）；回滚：不回写旧根，旧根数据只读保留（需求 `:476`）。

## 4. 审计双通道

### 4.1 两个 sink

| 通道 | 文件 | 归属 | 写什么 | 写失败降级 |
|---|---|---|---|---|
| **root audit**（profile 级） | `<home>/context-governance/root-audit-<profile>.jsonl` | 用户级；`apply` 即建（`AuditLog.#ensureFile` 现状） | 根生命周期、迁移、fail-closed、containment、根变化、身份、根限额 | in-memory 保留、logger warn、`/cg status` 的 `root-audit:` 行显 `failures=` |
| **per-root audit** | `<root>/memory/governance/audit.jsonl` | 每个纳管根；跟 store 同生命周期（P1 只有主根） | 会话级：压缩成本/loss、保护、回注、header、early、policy、子会话事件 | 沿用 T6 只读降级（`auditWriteFailures`/`auditSkippedReadOnly`），不阻断压缩 |

两个 sink 都复用 `AuditLog`（同一白名单/脱敏/8 MiB 轮转），只是 `file` 不同。`audit.maxBytes` 同时作用于两者。

### 4.2 事件归属迁移

| 事件 | 今天写哪 | P1 起写哪 | 理由 |
|---|---|---|---|
| `persistence-identity` | per-root | **root audit** | 身份/状态文件路径是 profile 级事实 |
| `inferred-fresh` | per-root | **root audit** | 主根首次推断，P1 只有主根 |
| `project-root-changed` | per-root | **root audit** | 根变化是根级事件 |
| 其余（`apply`/`capability*`/`policy*`/`header*`/`protection*`/`reinjection*`/`compaction-*`/`prune-observed`/`early-*`/`cycle-*`） | per-root | **不变** | 都是某个根内会话的事实 |

新增事件（root audit）：`root-registered`、`root-migrated`、`root-state-corrupt`、`root-state-write-failed`、`root-state-unsupported-version`、`root-entry-invalid`、`root-id-collision`、`root-fail-closed`、`root-limit-warn`、`root-audit-unavailable`、`containment-violation`、`root-unmanaged`（P1 过渡；每个会话一条，含 `sessionId/root/rootId`）。
`root-drift` 写 **pinned 根的 per-root audit**（managed 时；unmanaged 只 logger，P2 再补）。
P2 预留：`memory-tool-rejected`（§5）。

新增白名单字段：`rootId`、`rootCount`、`managed`、`fromVersion`、`toVersion`、`backupPath`、`violation`、`target`、`subagent`（boolean）、`source`（已有）。不新增任何正文类字段。

### 4.3 隔离规则（硬约束）

1. root audit **不写**会话正文、摘要全文、条目 detail；只写路径/键/计数/枚举/原因（沿用白名单）。
2. per-root audit **不写**其他根的事件、不写 profile 级迁移/registry 事件。
3. **跨根不写**：A 根会话的任何事件（含 cost/loss）不得落进 B 根 audit。P1 的 `unmanaged-root` 因此**不写 per-root audit**（P2 起写它自己的根 audit）。
4. 两个 sink 都只追加、不阻塞主流程。
5. 子会话的压缩/审计事件写**父根**的 per-root audit，并带 `subagent:true`；**不写记忆**（§5.3）。

### 4.4 `/cg status`：根集合视图（用户通用性缺口第 3 条）

```

roots: 3 (active=1, idle=2, fail-closed=0)
  root: id=3f2a9c1d4e5b6a7c name=DSH插件开发 project=DSH插件开发 state=active memory=42 audit=2026-10-26T13:30:00.000Z(apply)
```

- **全部纳管根**都列出（不截断；正常 ≤16，告警阈值见 §2.5）；每行 = `rootId` + 展示名 + project + 运行期状态 + 记忆条数 + 审计末行。

```js
createMemoryTools(store, {
```

### 5.2 错误码

| 码 | 条件 | 工具返回 | 审计 |
|---|---|---|---|
| `[NO_ROOT]` | cwd 缺失/无 `.git` 祖先（3A） | 拒绝，不读写 | **不审计**（完全不碰） |
| `[ROOT_UNMANAGED]` | 根已登记但 P1 未纳管（非主根） | 拒绝 | root audit `memory-tool-rejected`（`reason=unmanaged-root`） |
| `[ROOT_FAIL_CLOSED]` | 根存在但 `state=fail-closed` | 拒绝 | root audit `memory-tool-rejected` |
| `[ROOT_UNAVAILABLE]` | 身份不可用（fail-closed）/ store 打不开 | 拒绝或只读错误（按 store 现状） | root audit `memory-tool-rejected` |
| `[SUBAGENT_NO_MEMORY_WRITE]` | 子会话调 `mem_write` | 拒绝，不写 | 父根 audit `memory-tool-rejected`（`reason=subagent`） |
| `[BROKEN_ENTRY]` | 条目损坏被丢弃 | 拒绝 | root audit |

`memory-tool-rejected` 字段：`tool`/`code`/`root`/`rootId`/`sessionId`/`sessionShortId`/`subagent`/`reason`。

### 5.3 子会话（subagent = A）

- **判定**（宿主 `SessionHeader` 真实字段，`app.asar` 已核）：`session.header.origin === 'subagent'` 或 `session.header.parentSession !== undefined`；`isSubagent` 进 scope 结果。
- **纳管**：压缩观测、保护 journal、回注、成本/loss 审计**照常**（不得出现“被压缩但无保护/回注/成本”的子会话）。
- **不写记忆**：`mem_write` → `[SUBAGENT_NO_MEMORY_WRITE]`；`mem_query` **允许**（只读，且只读父根本根）。
- **不写持久记忆**：保护 journal 照写（回注需要），但**永不 materialize 进 topics/MEMORY.md**；周期结束（回注后）删除该 journal（P3 实现：`store.discardProtection(cycleKey)`）。P1 只记录策略，不实现。
- **header 注入**：**关闭**（需求 `:467`「不注入 header」、`:473` 第 8 条「子会话按第 2 条（不写记忆、不注入）」）；P1 只在 scope 里带 `isSubagent` 供 P3 接线。
- **审计**：事件写父根 audit，带 `subagent:true`；账本可按此分列。
- **根**：父根优先继承（不新增根）；父根未知才按自己 cwd 推断；再没有则 3A。

### 5.4 P1 落地范围

- 生产 `registerMemoryTools(ctx, store, { resolveStore, audit })` **恒注入 resolver**：managed → 当前根 store；`unmanaged` → `[ROOT_UNMANAGED]`；`no-root` → `[NO_ROOT]`；`fail-closed` → `[ROOT_FAIL_CLOSED]`；身份不可用 → `[ROOT_UNAVAILABLE]`。**不再用单 store 兜底放行**（审核 ②）。
- `mem_query` 接收 `exec`；`createMemoryTools(store, options)` 的默认单 store 只保留给单测/无 resolver 的显式构造。
- 跨根查询 1.0 不做：schema 不加根参数。
- P1 测试 5 条：resolver 收到 `exec`；`NO_ROOT`/`ROOT_UNMANAGED` 拒绝 + `memory-tool-rejected`；子会话 `mem_write` 拒绝且不调 resolver、`mem_query` 放行；默认单 store 不变；apply 接线（非主根/无根拒绝、主根放行、子会话写拒绝）。

### 6.3 实现要点

- `isWithin()` 用 `path.resolve` + 平台大小写归一（现有 `root-state.js:95-100` 已有雏形），**先 resolve 再比较**，不做字符串前缀。
- `realpath` 只在路径存在时做；不存在时按“父目录 realpath + 余下段”比较（防 junction 指向外部已存在目录）。
- **目录固定**：`DEFAULT_CONFIG.memoryRoot` 改为常量 `memory/governance`（现默认 `.dsh/memory`）；`memoryRoot` 配置键保留为**兼容输入**，但值只允许 `memory/governance`（`/`、`\` 归一后比较），其他值（含绝对、`..`、别的相对路径）→ **该根 fail-closed**，不静默改写、不回退到 `.dsh/memory`。
- `resolveConfig` 只做**静态**校验（非空、相对、无 `..`）；每根 `resolve` 后的 **containment 在 attach/open 时做**（因为 root 运行期才知道）。
- **不新增“自定义目录”**；不因迁移去读/写旧 `.dsh/memory`（需求：记忆不迁移、不删除，留在原路径）。
- `rootId` 计算只读字符串（不碰文件系统）；UNC/长路径归一在 `canonicalRoot` 里做一次。
