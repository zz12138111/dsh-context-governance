# M2 需求草案 v0.4 —— 提前压缩 + 策略 + 成本账本

> 状态：草案 v0.4，供评审复核；v0.3 → v0.4 变更见 §12。
> 日期：2026-10-25
> 依据：架构 v1.1 §6/§8/§14；DSH asar 只读调研；外部评审两轮意见；用户 2026-10-25 决定。

---

## 0. 一页摘要

**M2 只做一件事的主线：提前压缩，省上下文、去掉过时信息，并把账算清楚。**

- **提前压**：`compact.at` 低于宿主原生触发点时，我们在安全时机主动压一次；
- **策略**：四层配置 + profile 标签 + 偏好默认值，全部可解释；
- **账本**：每次压缩与每次决策留痕，能回答“提前压赚了多少、花了多少”；
- **不做抑制**：宿主原生触发点（≈67.85%）保持原样，我们只在它之前动手，不拦它。

**不做**：不造引擎、不换摘要后端、不接管 provider、不包装宿主决策点、不做 UI 仪表盘、不做货币成本。

---

## 1. 背景与关键事实

### 1.1 DSH 原生机制

- 引擎在 **agent preset** 内：`thresholdRatio 0.8` + `headroomTokens 65536`；
  `native = floor(min(W×0.8, W−O−65536))`，1M 窗口/256k 输出预留下 ≈ **678k ≈ 67.85%**。
- **preset 平面任何 patch 层都够不到**。
- 取引擎唯一路径：`agentPresets.serviceFor(agent, 'compaction')`。
- 引擎契约：`compactIfNeeded` / `compactNow` / `compactRegion`；手动 `/compact` 即 `compactNow`。
- 宿主自己的压力检查在 `pre-step`（两步之间）。

### 1.2 生态

| 插件 | 角色 | 与 M2 关系 |
|---|---|---|
| `compaction-basic` | 原生引擎 | 只调它的 `compactNow`，不包装、不改 |
| `context-zip` | 替换摘要 | 不动；`compactNow` 走它生成的摘要 |
| `tool-result-pruner` | 压缩点折叠大工具结果 | 不动 |
| `dsh-context` | 上下文/成本可视化 | 不重复做图表；我们做策略效果账本 |
| `dsh-compact` | 第三方闸门（抑制型） | **不采用**，见附录 A |

### 1.3 本机实测

- 本插件 scope 拿不到 `ctx.compaction`（`strict=false → undefined`）；
- `tokenMeter` = chars/4 估算，本例**低估约 28%**；
- `usage`（`assistant/message`）= 实测，滞后一步；
- 手动 `/zip-compact` 不触发 `pruneSession`。

## 2. 目标（可验收）

1. **提前压可用且默认开**：`compact.at` 低于宿主原生点时，于安全时机主动压一次。
2. **每层可配**：内置 / 插件配置 / 项目 `.cg-policy.json` / 会话覆盖。
3. **可解释**：`/cg status` 打印合成链、宿主原生点、当前压力、最近一次决策。
4. **可审计**：每次判断、主动压、跳过、失败都有记录。
5. **成本可见**：按会话/项目/天/模型聚合；实测与估算分列；能回答“提前压赚了多少”。
6. **与记忆协作**：显式 profile 打标；偏好只作默认值（`active` 才生效）。

## 3. 非目标

- **不做“推迟/抑制”**（不包装 `compactIfNeeded`，不拦截宿主决策）；
- 不造引擎、不换摘要后端、不接管 provider、不改 preset 平面；
- 不做 UI 图表、不做货币成本、不做跨机同步；
- 不改 pruner / 折叠 / spill；
- 不做行为推断自动打标。

## 4. 组成

### 4.1 策略层（0.2.0）

四层：内置 → 插件配置（`cordis.patch.yml`）→ 项目 `<project>/.cg-policy.json` → 会话 `/cg set`。

| 参数 | 含义 | 默认 | 范围 |
|---|---|---|---|
| `compact.at` | 压力到多少比例就提前压 | `0.60` | `0.20` ~ **`native` 动态上限** |
| `compact.early` | 允许提前压 | **`true`** | bool |
| `compact.cooldownMin` | 两次压缩最小间隔 | `10` | 分钟 |
| `compact.minDeltaTokens` | 距上次压缩至少新增 token | `20000` | token |
| `compact.estimateSafety` | 估算放大系数 | `1.35` | `1.0–1.6` |
| `compact.lowThresholdAck` | 允许 `<0.30` | `false` | bool |
| `reinject.maxChars` / `maxLines` | 回注预算（既有） | 800 / 8 | 既有 |

- **动态上限**：`compact.at` 超过宿主原生点（≈0.6785）时**直接拒绝**，错误信息写明“超过原生触发点，M2 不支持推迟”。
- 校验：白名单键；未知键或越界 → 拒绝该层 + `policy-invalid` 审计，退回上一层。
- 解释：`/cg status` / `/cg policy show` 打印合成链与 `native`、`safe-cap`。

### 4.2 提前压（0.2.1，核心）

**取引擎**：`agentPresets.serviceFor(agent, 'compaction')`；拿不到 → 能力不可用，`/cg status` 标 `early=unavailable`，其余功能照常。

**执行流程**

1. 在安全时机（候选：`step/end`、`turn/end`，由 G2 定）读取当前会话；
2. `pressure = max(上一次 usage 实测比例, 估算比例 × 1.35)`；
3. 满足全部条件才压：
   - `pressure ≥ compact.at`；
   - `pressure < native`（超过原生点就交给宿主，别抢）；
   - 距上次压缩 ≥ `cooldownMin` **且** 新增 ≥ `minDeltaTokens`；
   - agent 处于可压缩状态（不忙）。
4. 调 `compactNow(agent, signal)`；成功后照常走事件流（start→summary→checkpoint→end），我们的保护与回注自动参与；
5. 失败：指数退避，最多 3 次；仍失败则记 `early-failed`，**不打断会话**，等宿主原生压缩兜底。

**审计**：`early-decision`（pressure/policy/source/decision）、`early-forced`、`early-skipped(reason)`、`early-failed`。

**硬约束**

1. 我们**不在宿主的调用路径里**，任何失败都不影响宿主压缩——它照旧在 native 点自己压。
2. 绝不打断正在执行的工具调用或模型流。
3. 忙或时机不当时**放弃本次**，记 `early-skipped(busy)`，绝不重试风暴。

### 4.3 成本账本（0.2.2）

- 数据源：`compaction-cost`（`cost-v1.2`）+ `early-decision` / `early-forced`。
- 聚合：`sessionId` / `project` / `day` / `model` / `backend`。
- 命令：`/cg cost [--by day|project|model] [--since …]`。
- 预算：只提示（`budget.warnAt`），不阻断。
- 口径：`usage` = measured；`tokenMeter×safety` = estimate；不混算；未知保持 unknown。

**提前压收益口径**

```
tokensSavedPerRequest = 压缩后首条请求 usage − 压缩前最后一条 usage   (measured)
summaryCost           = 本次压缩调用的 usage                          (measured)
benefitEstimate       = tokensSavedPerRequest × 预计剩余请求数 − summaryCost   (estimated，须标假设)
```

- 只给两个实测数 + 一个显式标注假设的估算；不给单一确定数。
- “预计剩余请求数”默认按本会话历史平均每轮请求数估，可配置覆盖。

### 4.4 表面与命令

```
/cg status               # 策略链 + native/safe-cap + 当前压力 + 最近 early 决策 + last-cost
/cg policy show          # 解释当前生效来源与合成过程
/cg set compact.at=0.5   # 会话覆盖
/cg compact now [--force]# 手动立即压；冷却期内需 --force（两步确认）
/cg cost [--by …]        # 账本
```

## 5. 会话特点与偏好

- **profile 显式打标**：`batch` / `coding` / `research` / `review`；不自动推断。
- 默认参数表：

| profile | compact.at | 回注预算 |
|---|---|---|
| `batch` | 0.45 | 400 / 4 行 |
| `coding` | 0.60 | 800 / 8 行 |
| `research` | 0.67（≤native） | 1600 / 16 行 |
| `review` | 0.55 | 800 / 8 行 |

> 注：`research` 原设 0.75 因超出 native 被下调到 0.67；这正好说明“推迟不可用”后参数必须受 native 约束。

- **偏好**：`type=preference` 且 `status=active` 才影响默认值；`proposed` 不生效。
- **合成顺序**：显式层（会话 > 项目 > 插件）> 标签层（profile/偏好）> 内置默认。

## 6. 安全机制

### 6.1 估算误差（M2.1 静态）

```
pressure = max(上一次 usage 实测比例, 估算比例 × 1.35)
```

- 1.35 为全局值（28% 低估换算 ≈1.39，留余量）；
- **M2.2 再做自校准**：账本记录“同一时刻 usage vs 估算”成对样本，积累后按模型取 p90。

### 6.2 冷却与相对增量

时间冷却（`cooldownMin`）+ 增量冷却（`minDeltaTokens`）双条件，避免阈值边缘反复压。

### 6.3 失败不影响宿主

我们不在宿主决策链上：取不到引擎、调用失败、退避耗尽，最多是“没提前压”，宿主仍在 native 点正常压缩。所有失败写审计，不静默。

### 6.4 忙时顺延

压力到了但时机不可用（agent 忙）→ 放弃本次，`early-skipped(busy)`，等下一个安全时机或宿主原生压缩；不打断、不重试风暴。

### 6.5 为什么不包装宿主引擎

包装（wrap `compactIfNeeded`）能实现“推迟”，但风险高：双重包装、失败路径影响宿主压缩、与第三方闸门冲突。**本期明确不做**；若未来要做，单独立项、单独实验、单独验收。

## 8. 验收标准（草案）

1. **提前压生效**：`compact.at`（如 0.60）时在安全时机压一次；`early-forced` 审计；事件流完整。
2. **不抢宿主**：压力已过 native 时不主动压，交由宿主（审计 `early-skipped(above-native)`）。
3. **失败不伤宿主**：模拟 `compactNow` 抛错 → 会话继续，宿主仍能压，`early-failed` 有记录。
4. **忙时顺延**：模拟忙 → `early-skipped(busy)`，不打断、不重试。
5. **防抖**：cooldown + minDelta 双条件生效。
6. **手动压两步**：冷却期内无 `--force` 返回提示；带 `--force` 执行并审计。
7. **参数约束**：`compact.at > native` 被拒绝，错误信息明确。
8. **可解释**：`/cg status` 打印合成链、native、当前压力、最近决策。
9. **账本**：两个实测数 + 标注假设的估算；聚合 = 逐条求和。
10. **记忆协作**：`proposed` 偏好不生效。
11. **不回归**：M1 的 S1–S6 通过；生产代码仍无折叠、**无引擎包装**。

## 附录 A：“推迟”的能力说明与代码可行性（不纳入 M2）

保留此节仅为记录，**不实现、不测试、不验收**。

**原理**：包装 preset 作用域引擎的 `compactIfNeeded`——压力 < 策略点时返回 `null`（引擎不跑），到点再调用原方法。等价于把压缩点从 native 往后推。

**可行性**：方法存在且可包装（`agentPresets.serviceFor(agent,'compaction')` 返回对象，方法可被替换）；外部插件 dsh-compact 已验证该路径。

**为什么不纳入**：
1. 可用区间极窄：1M 窗口/256k 预留下，native 678k、硬上限 744k，只有约 6.6 个百分点；
2. 风险高：包装后我们的代码进了宿主决策链，失败路径可能堵死压缩；双闸门冲突、死锁、溢出风险都由第三方 README 自身记录过；
3. 收益低：推迟只会增加每请求成本、减少摘要次数，与用户“省上下文”的核心目标相反。

**若未来要做**：单独立项（如 M3），先做隔离实验（纯净 / context-zip / 第三方闸门三环境），再谈实现。
