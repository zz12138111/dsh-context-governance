## 0. 一页摘要

M2 把插件的角色从**观察者**变成**调度者 + 记账者**，但只在“压缩”这一件事上：

- **策略**：每个会话/项目可以规定“上下文用到多少就压缩”（`compact.at`），四层覆盖、来源可解释；
- **闸门**：在宿主“要不要压”的决策点上按策略放行或抑制；需要提前压时主动调用一次；
- **账本**：每次决策与压缩都记录，能回答“为什么这次压了/没压、省了多少、花了多少”。

**不做**：不造压缩引擎、不替换摘要后端、不做 provider 接管、不做 UI 仪表盘、不做货币成本。

---

## 1. 背景与关键事实

### 1.1 DSH 原生机制（调研确认）

- 压缩引擎挂在 **agent preset** 里，出厂 `thresholdRatio: 0.8` + `headroomTokens: 65536`；
  有效触发点 = `floor(min(W × 0.8, W − O − 65536))`，1M 窗口下 ≈ **67.85%**。
- **preset 平面任何 patch 层都够不到**：profile `cordis.patch.yml` 里写的 `thresholdRatio` 对有效触发点无效。
- 引擎可从 preset 作用域取出：`agentPresets.serviceFor(agent, 'compaction')`（宿主任 agent-preset-registry）。
- 引擎契约三个操作：`compactIfNeeded`（自动压力/溢出）、`compactNow`（显式按需）、`compactRegion`（指定范围）。
- 手动 `/compact` 的处理器就是 `ctx.compaction.compactNow(agent, signal, commandId)`。

### 1.2 生态现状（避免重复造）

| 插件 | 角色 | 与 M2 的关系 |
|---|---|---|
| `compaction-basic` | 原生引擎 | 我们的闸门包它的决策点，不改引擎 |
| `context-zip` | 替换摘要（五段式交接 + 分段检索） | 不动；闸门对它同样生效 |
| `tool-result-pruner` | 压缩点折叠大工具结果 | 不动；折叠已被 M1.1 判定取消自研 |
| `dsh-context`（已装） | 上下文/token/成本**可视化** | **不重复做图表**；我们做“策略效果账本” |
| `dsh-compact`（第三方，未装） | 按路由比例的**闸门** | 证明闸门可行；需共存检测 |
| Claude Code | `autoCompactWindow` / 环境变量控制自动压缩窗口 | 同类思路的外部佐证 |

### 1.3 本机实测事实

- `ctx.compaction` 在本插件 scope **未提供**（`strict=false → undefined`）→ 只能经 `agentPresets` 拿引擎；
- `tokenMeter` 是 **chars/4 估算**（本例低估约 28%），只能当“估算来源”；
- `usage`（`assistant/message`）是**实测**，但滞后（下一次调用才有）；
- 手动 `/zip-compact` **不触发** `pruneSession`，只有自动压缩调 pruner。

## 2. 目标（可验收）

1. **每层可配**：`compact.at` 可在内置默认 / 插件配置 / 项目配置 / 会话覆盖四层设置，取值 `0.30–0.85`。
2. **可解释**：`/cg status` 能打印“当前生效值来自哪层、被谁覆盖、宿主原生触发点是多少”。
3. **可按策略压缩**：到点前抑制、到点后交还宿主；低于宿主原生触发点时用 `compactNow` 主动压。
4. **决策可审计**：每次闸门判断与每次主动压缩都写审计（`gate-decision` / `gate-forced`）。
5. **成本可见**：按会话/项目/天/模型聚合 `compaction-cost`，实测与估算分列，未知保持 unknown。
6. **与记忆协作**：会话 profile 显式打标；`type=preference` 且 `status=active` 的偏好只作为默认值来源，`proposed` 不生效。

## 3. 非目标（明确不做）

- 不做压缩引擎、不替换摘要后端、不接管 provider、不改 preset 平面；
- 不做 UI 仪表盘、不做图表（`dsh-context` 已有）；
- 不做货币成本换算、不做跨机同步；
- 不改 `tool-result-pruner` / 折叠 / spill；
- 不做“行为推断自动切档”（推断只能给建议，不自动生效）。

## 4. 组成

### 4.1 策略层（0.2.0 交付）

- **四层**：内置默认 → 插件配置（`cordis.patch.yml`）→ 项目配置 → 会话覆盖。
- **项目配置**：`<project>/.cg-policy.json`（文件名待定），只放差异。
- **会话覆盖**：`/cg set compact.at=0.5`，存 `~/.dsh/context-governance/sessions/<sessionId>.json`，只影响该会话。
- **参数集（初版）**：

| 参数 | 含义 | 默认 | 范围 |
|---|---|---|---|
| `compact.at` | 上下文压力到达此比例即压缩 | `0.60` | `0.30–0.85` |
| `compact.cooldownMin` | 两次主动压缩最小间隔 | `10` | 分钟 |
| `compact.passOverflow` | 溢出救援是否永远放行（只读项，不可关） | `true` | 固定 |
| `reinject.maxChars` / `maxLines` | 回注预算（既有） | 800 / 8 | 既有 |

- **校验**：白名单键；未知键或越界 → **拒绝该层**并写 `policy-invalid` 审计，DSH 照常跑，退回上一层。
- **解释**：`/cg status` 输出合成链。

### 4.2 闸门层（0.2.1 交付，核心）

- 取引擎：`agentPresets.serviceFor(agent, 'compaction')`；
- 包装 `compactIfNeeded`：
  - 压力 < `compact.at` → 返回 `null`（不压）；
  - 压力 ≥ `compact.at` → 调用原方法（宿主照常压）；
  - `trigger` 为溢出救援 → **永远透传**。
- 提前压：压力远低于宿主原生点时，若策略要求更早，调用 `compactNow`（需 agent 空闲，失败要审计、不重试风暴）。
- 决策审计：`gate-decision { measured, policy, source, decision, trigger }`。
- 共存：检测到引擎已被其他插件包装（同方法已被替换 / 已知 guard 字段）→ **告警并禁用闸门**，不双包。

### 4.3 成本账本（0.2.2 交付）

- 数据源：既有 `compaction-cost`（`cost-v1.2`）与 `gate-decision`；
- 聚合维度：`sessionId` / `project` / `day` / `model` / `backend`；
- 命令：`/cg cost [--by day|project|model] [--since …]`，输出周期数、shadowed、summary、injected、dropped、pruned、并注明来源；
- 预算：只提示（`budget.warnAt`），不阻断；
- 口径：`usage` = measured；`tokenMeter` = estimate(`chars/4`)；两者不混算、不互相比较；未知保持 unknown。

### 4.4 表面

`/cg status` 增加：
```
policy: compact.at=0.50 (source=session)
  chain: builtin 0.60 → profile(review) 0.55 → session 0.50
  host-native ≈0.6785  gate=active
last-gate: measured=612k(61.2%) decision=skip at 2026-10-25T…
last-cost: before=… after=… pruned=… tools=…
```

## 5. 会话特点与偏好的结合

**输入三层，从软到硬**：

1. **会话 profile 标签**：`batch` / `coding` / `research` / `review`（显式打标，不自动推断）；
2. **记忆偏好**：`type=preference`、`status=active` 的条目影响“默认值”；`proposed` 不生效；
3. **配置层**：项目默认、会话覆盖。

**profile 默认参数表（草案）**：

| profile | compact.at | 回注预算 | 说明 |
|---|---|---|---|
| `batch` | 0.45 | 400 / 4 行 | 长跑、重复内容多，早压省摘要成本 |
| `coding` | 0.60 | 800 / 8 行 | 保代码上下文 |
| `research` | 0.75 | 1600 / 16 行 | 资料多，晚压保细节 |
| `review` | 0.55 | 800 / 8 行 | 结论导向 |

**合成顺序**：会话覆盖 > 项目配置 > profile/偏好默认 > 内置默认。

**约束**：偏好不能绕过用户生效；模型提出的偏好必须先经用户确认（`proposed → active`）。

## 7. 验收标准（草案）

1. 四层覆盖正确，非法配置被拒绝且可追溯；`/cg status` 打印完整合成链；
2. 闸门可把压缩推迟到策略点（用真实会话证明：跳过 → 到点压）；
3. 提前压路径可用（`compactNow`），失败有审计且不重试风暴；
4. 溢出救援路径**从未被拦截**（用测试/回放证明）；
5. 成本聚合 = 事件逐条求和；实测/估算分列；无数据为 unknown；
6. 与记忆的协作符合第 5 节：`proposed` 偏好不生效；
7. 全量测试通过；M1 的 S1–S6 不回归。

## 9. 待外部评审的问题

1. **闸门是否可接受**：包装宿主引擎的决策点，是否越过“治理层”边界？是否应改为“只建议不干预”？
2. **共存策略**：与 `dsh-compact` 等同类插件同时安装时，谁让路？检测到已包装就禁用，够不够？
3. **与 `dsh-context` 的边界**：成本部分我们只做“账本/审计”，不做图表，这个切分是否合理？
4. **参数范围**：`0.30–0.85` 是否合适？是否需要更低（更早压）的极端档？
5. **偏好接入策略**：让 active 偏好影响默认值，是否违背“用户显式控制”原则？
6. **profile 打标**：只做显式打标是否足够？是否需要从记忆进度自动建议？
7. **提前压的成本**：每压一次都是一次摘要调用，是否应默认关闭“提前压”，只保留抑制？
