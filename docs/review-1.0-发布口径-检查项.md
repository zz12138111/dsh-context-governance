### 4.2 通道与安全边界（需求锁死）

- **默认值 = 开**：配置解析默认 `true`；`/cg status` 显示 `on (default)`（不得显示成“会话开启”）。
- **项目层禁止**：`.cg-policy.json` 里出现 `compact.early.armed`（无论 true/false）→ **忽略并写 `policy-invalid`**（含 key 与原因），不得因恶意仓库打开或关闭真实压缩；需单测。
- **不做环境变量**：全仓 grep `process.env` 无 armed 相关键；需断言。
- **命令**：`/cg compact arm` / `/cg compact disarm`（会话级）；`arm` 因默认已是开，若保留则用于“会话内重新开启”，必须与 status/audit 一致。
- **审计族**：`early-armed` / `early-disarmed` 与 `early-decision/skipped/forced/aborted/failed` 同族，白名单字段受控、无正文。
- **不可逆提示**：默认开之下不会每次弹确认，故 release notes 必须写明“超过阈值会真实压缩、原文只留记忆指针；可用 `/cg compact disarm` 关闭；项目配置不能打开、只能关闭”。

### 4.3 R-2 门禁（隔离 profile，≥1 次真实提前压）

一次可复核证据，缺一不可：
1. 隔离 profile 中会话越过 `at` 且低于 `native−0.02` → 真实触发；
2. `early-forced` 审计（`compaction=committed`、`protection=ok|failed|null`、`reinjected`、`delayMs`）；
3. 对应 `compaction-cost`（`tokensBefore/After` + 来源）；
4. `/cg status` **原文落盘**（`analysis/…/status-<时间>.txt`），不得只贴摘录；
5. 触发前后 `header-injected`/记忆未被破坏（保护 + 回注的证据）。

### 4.7 两条必须写准的口径（00 要求固化）

1. **`/cg status` 的 `adapter=` 不是“后端已识别”**：它是插件侧推断结果；隔离实测 context-zip 下仍显示 `host-basic (inferred)`。发布物/README 说明后端能力时，**只能引用 profile 的 redirect + bundle**（如 `0.1.0-context-zip` + `dsh-context-zip`），不得写“status 显示 context-zip 即已识别”。
2. **`trigger=manual` ≠ 用户手动压缩**：插件提前压走宿主 `compactNow(agent, signal, 'early-auto')`，宿主按 `sourceCommandId != null` 记为 manual。发布物描述自动提前压时，**不得写成“用户手动压过”**；需要区分时写“宿主 manual API 路径（含插件自动触发）”。

### 4.8 已知限制：记忆自动去重未实现（P2-4 第 3 条 → 1.1）

**判定（审核）**：**不是纯写入侧优化**——旧条目会留在 `active`，可能被读到。依据代码：
- `header.js:81` 按 `updatedAt` **降序**；每类配额固定（`todo 2 / progress 2 / decision 2 / anchor 1 / preference 1`）。同类型 `active` 超过配额时，**旧条目会被一并注入**（新条在前，旧条填剩余配额）。
- `mem_query` 返回全部 active 条目；`/cg status` 的 `active` 计数会偏高。
- **但**：`mem_write` 已支持显式 `supersede`（`op=supersede` 或 `supersedes` 字段），不是“无法去重”；缺的是**自动检测/自动 supersede**。
- 不会造成状态机错乱（状态仍由显式操作驱动），也不会影响压缩/保护/回退。

**发布说明写法（可直接用）**：

> **记忆自动去重未实现（计划 1.1）**：同一事项重复写入时，插件不会自动用新条目取代旧条目。可能出现多条 `active` 记忆，且当同类条目多于 header 配额（progress/todo/decision 各 2）时，**旧条目的内容也会被注入新会话**；`/cg status` 的 `active` 计数也会偏高。缓解：写入时用 `mem_write` 的 `supersede` 显式取代旧条目，或先 `expire` 旧条目。该限制不影响压缩、保护、回注与回退，也不改变已写入条目的状态。

**分类**：中等风险的数据卫生问题（可读到过期条目），**不阻塞 1.0**；但发布说明必须写，且不能写“不会读到旧条目”。

### 4.10 1.0 缺陷：跨项目会话被提前压但零保护/零记账（→ 发布阻塞判断）

**事实**（`analysis/req-20261025-12/1.0-缺陷-提前压跨项目无保护.md` + 代码核对）：
- `runtime.js` 的 `#belongsToProject` 对外项目会话直接 `return`（设计：不写本项目记忆、不回注别的会话）——这层正确；
- `early-wiring.js check()` **没有同源过滤**；`index.js` 接线未传 `projectRoot` → **动作跨项目、观测不跨**；
- 结果：外部工作区会话 `effective ≥ at` 会被真实压缩，但**无 `protection-write`、无 `reinjection`、无 `compaction-cost`**；首个实证是 00 会话（cwd `G:\DS-HARNESS`，0.602→0.065，只有 `compact-checkpoint`）。
- `early-forced` 的 `compaction:"committed"` 是 fallback：没有 fresh report 也写 committed（`early-wiring.js:172` 一带），审计语义误导。

**1) 是否阻塞 1.0（审核判断）**：**应阻塞“默认开”的 1.0 发布**，理由：
- 不是边缘场景：profile 级安装 + 默认开 = 本机**任意工作区**会话都可能中招；首个实证就是 00 自己的会话；
- 防护承诺被绕过：保护/回注/成本是本插件对“不可逆压缩”的唯一交代，外部会话三者全无，且审计看起来还有 `committed`；
- 修复成本低（wiring 加同源过滤 + 审计 skip），先修再发比带缺陷发划算。
- 是否接受带缺陷发由用户决定，但**我不写“风险可控/已接受”**。

**2) 若用户选择带缺陷发——Release notes 可用措辞**：
> **已知缺陷（1.0 默认开启，未修复）：提前压会作用于本机所有工作区的会话，但保护与记账只覆盖插件配置的项目根。** 具体：非本项目工作区的会话达到 `compact.at` 时会被真实压缩，但**不会写入保护项、不会回注、不会记录 `compaction-cost`**；审计只留一条 `early-forced`，其中 `compaction=committed` 是占位值，无法据此追溯压缩内容。首个实证：00 工作区会话（effective 0.602 → 0.065，仅 `compact-checkpoint`）。**规避**：在插件配置设 `compact.early.armed=false`（全局关闭提前压），或只在单一项目工作区使用本插件。该缺陷未修复；是否在修复前使用由用户自行判断。

**3) §4.10.3 若选择“先修再发”——复核要补的验证（六条）**：
1. 外部工作区会话（cwd 不在 `projectRoot`）→ **skip + 审计 `early-skipped reason=foreign-session`**，`compactNow` 调用 **0 次**、无 `early-decision force`；
2. 本项目会话对照：仍产生 `protection-write` → `materialized` → `reinjection` → `compaction-cost` 四件套；
3. 同一实例内“本项目 + 外项目”两会话并存，互不串写；`guard.ignoredForeignEvents` 与 wiring 判定一致（同一词法比较）；
4. `onlyProject` 关闭时的行为明确（外项目是否仍 skip）；
5. `/cg status` 能看到 skip 原因/foreign 计数；
6. 全量测试 + 新增 spy 用例。

**4) `committed` fallback**：**单独立项**（审计语义缺陷，与跨项目修复解耦）。要求：无 fresh report 时 `compaction` 写 `null`/`unknown`，不写 `committed`；补单测。它会让跨项目缺陷更显眼，但即使跨项目修好，本项目会话在“accepted 但无新报告”的边缘路径下同样会误写。

### 4.11 发布缺陷与阻塞清单（每条独立结论）

| 编号 | 缺陷 | 结论 |
|---|---|---|
| **B-1** | 压缩动作跨出项目范围、保护/账本不跨：① `early-wiring` 无同源过滤，外部工作区会话被真实压缩但无 `protection-write` / `reinjection` / `compaction-cost`；② 同一根因下，外部会话的**宿主原生压缩**同样零保护零账本（`runtime.js:1456` 单点 return，所有 `session/event` 一律跳过） | **阻塞「默认开」的 1.0 发布。** 不因阈值高低消失；`armed=false` 规避只挡提前压、不恢复外部会话的保护（Release 必须写清） |
| **B-2** | `early-forced` 的 `compaction:"committed"` 是无 fresh report 时的 fallback，审计语义误导 | **不阻塞发布**（但必须写进 Release 已知缺陷段：该字段是占位值，不能作为压缩证据）。它不改变压缩行为、不增加不可逆损失，影响的是可追溯性 |
| B-3 | 清史与 B-1/B-2 修复的先后 | 流程项、非缺陷：**清史在前 → 修复在后 → public 最后**（理由与流水线见 `docs/公开仓库方案-1.0.md` §8.1）；不返工前提是「清史前不再推新提交」 |

**B-1 的第二个实证面（00 会话，2026-10-26）**：19:15:58 插件 `early-forced`；19:26–19:28 之间宿主**原生**压缩一次（中间无 `early-forced`，有效压力 0.591→0.246）。该会话全生命周期 `protection-write=0`、`compaction-cost=0`、`reinjection=0`。**并入 B-1 的依据**：原生压缩与提前压共用同一个「外来会话跳过点」（`runtime.js:1456`），不是新根因；它证明「保护/账本」实际只覆盖本项目会话，且「关掉提前压」并不为外部会话恢复保护。故不单独立项。

> 关于「调高 `compact.at` 能否**替代**修 B-1」：**不能替代**。它解决的是「默认值下触发概率/默认暴露面」，没解决「一旦触发即零保护、零账本、审计占位」的机理——阈值之上照样命中，且把风险解释成「用户自己调低」等于转嫁。它只能作为「带缺陷发」时的附带缓解，且必须与 Release 已知缺陷段同时存在。
