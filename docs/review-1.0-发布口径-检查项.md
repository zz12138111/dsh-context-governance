### 4.8 已知限制：记忆自动去重未实现（P2-4 第 3 条 → 1.1）

**判定（审核）**：**不是纯写入侧优化**——旧条目会留在 `active`，可能被读到。依据代码：
- `header.js:81` 按 `updatedAt` **降序**；每类配额固定（`todo 2 / progress 2 / decision 2 / anchor 1 / preference 1`）。同类型 `active` 超过配额时，**旧条目会被一并注入**（新条在前，旧条填剩余配额）。
- `mem_query` 返回全部 active 条目；`/cg status` 的 `active` 计数会偏高。
- **但**：`mem_write` 已支持显式 `supersede`（`op=supersede` 或 `supersedes` 字段），不是“无法去重”；缺的是**自动检测/自动 supersede**。
- 不会造成状态机错乱（状态仍由显式操作驱动），也不会影响压缩/保护/回退。

**发布说明写法（可直接用）**：

> **记忆自动去重未实现（计划 1.1）**：同一事项重复写入时，插件不会自动用新条目取代旧条目。可能出现多条 `active` 记忆，且当同类条目多于 header 配额（progress/todo/decision 各 2）时，**旧条目的内容也会被注入新会话**；`/cg status` 的 `active` 计数也会偏高。缓解：写入时用 `mem_write` 的 `supersede` 显式取代旧条目，或先 `expire` 旧条目。该限制不影响压缩、保护、回注与回退，也不改变已写入条目的状态。

**分类**：中等风险的数据卫生问题（可读到过期条目），**不阻塞 1.0**；但发布说明必须写，且不能写“不会读到旧条目”。

### 4.10 1.0 缺陷：跨项目会话被提前压但零保护/零记账（→ 发布阻塞判断）

**事实**（`analysis/req-20261025-12/1.0-缺陷-提前压跨项目无保护.md` + 代码核对）：
- `runtime.js` 的 `#belongsToProject` 对外项目会话直接 `return`（设计：不写本项目记忆、不回注别的会话）——这层正确；
- `early-wiring.js check()` **没有同源过滤**；`index.js` 接线未传 `projectRoot` → **动作跨项目、观测不跨**；
- 结果：外部工作区会话 `effective ≥ at` 会被真实压缩，但**无 `protection-write`、无 `reinjection`、无 `compaction-cost`**；首个实证是 00 会话（cwd `G:\DS-HARNESS`，0.602→0.065，只有 `compact-checkpoint`）。
- `early-forced` 的 `compaction:"committed"` 是 fallback：没有 fresh report 也写 committed（`early-wiring.js:172` 一带），审计语义误导。

**1) 是否阻塞 1.0（审核判断）**：**应阻塞“默认开”的 1.0 发布**，理由：
- 不是边缘场景：profile 级安装 + 默认开 = 本机**任意工作区**会话都可能中招；首个实证就是 00 自己的会话；

- 修复成本低（wiring 加同源过滤 + 审计 skip），先修再发比带缺陷发划算。
