## 3. 适配器契约（实现值）

| 维度 | 宿主 `compaction-basic` | context-zip（接管行） | 未知 provider |
|---|---|---|---|
| 控制权 | `host-pressure` | `host-pressure` | `unknown` |
| 感知层级 | `event` | `event` | `none` |
| 触发面 | `compaction-event` + `command` | 同左 | `compaction-event` |
| 前后钩子 | `before: best-effort`（start 通知，无否决）/ `after: event` | 同左 | 同左 |
| 摘要权威 | `exclusive` | `exclusive` | `exclusive` |
| 摘要可读性 | 首次压缩后由文本判定；空摘要 → `unreadable` | 预置 `readable`；每篇按五段标题校准 | `unknown` |
| 改写边界 | `replace-span`；工具配对由宿主维护 | 同左 | `unknown`/`replace-span`（不据此行动） |
| 保护角色 | `validator`（只读校验） | 同左 | `validator` |
| 可观测性 | usage/range/artifact 均 true | 同左 | true（未验证） |
| 版本矩阵 | host `0.2.1-rc.2` | backend `0.1.10`（unknown 时只告警） | unverified |

识别规则（按顺序）：
1. 无 `ctx.compaction` → `none`；
2. 有 `compactNow` 且存在 `undoManualSeat` / `declaredConfig` / 类名 `ContextZipEngine` → `context-zip`；
3. 类名 `BasicCompactionEngine` 或有 `compactIfNeeded` → `host-basic`；
4. 其余 → `unknown`（不猜、不接管）。

自检（初始化）检查：`compaction-service`、`event-api`、`host-version`、`backend-version`、`summary-readability`。任一项 `fail` → 自检失败；`pending`（摘要未出现）不阻断 full。

## 4. 保护校验

### 4.1 检查项与判定

| 检查 | 判定 | 失败含义 |
|---|---|---|
| `artifact` | summary 事件存在、shadow 区间能落到快照 surface、checkpoint 存在且出现在压缩后 surface | 无法核对（缺产物/错位） |
| `latest-user-message` | 最新 `user/message`（`source.kind=user`）不在 shadow 区间，且压缩后仍在 surface | 最新用户消息被吞 |
| `rule-injection` | shadow 的 `system-prompt`/`agent-instructions`/`skill-catalog` 必须有**更新的同类副本**留在 surface | 规则注入无后续副本 |
| `tool-pairing` | shadow 前切口、后切口的累计 tool-call/result balance 均为 0；无孤儿结果；替换后仍为 0 | 切口拆散配对 |
| `batch-list` | **同一条**人类 `user/message` 或 `assistant/message` 正文里，必须**同时**出现批次语义（`批次\|进度\|progress\|batch`）与“数字/数字”明确比例（`511/958`、`8000/1500`）；排除 `tool/*`、JSON/代码块载荷、`YYYY/MM` 日期；最新候选未被 shadow 时 pass，被 shadow 时摘要必须覆盖其全部比例；无候选或无法核对一律 `skip`（`no-batch-semantics`/`date-like-ratio`/`no-ratio-in-user-messages`） | 批次进度丢失 |
| `rollback-point` | 最新回滚/备份消息未被 shadow；被 shadow 时摘要必须含关键词且覆盖至少一个路径 | 回滚点丢失 |
| `summary-readable` | `compaction/summary.summary` 非空；空 → `warn` + `degraded` | 摘要不可读（降级，不误报 fail） |

规则注入检查接受“旧快照被吞 + 新 baseline 已注入”的情况（宿主会在后续 turn 重新注入 `agent-instructions`，本次实测 16/16 有这个现象）；否则判 fail。

**batch 判据演进（0.1.13 → 0.1.14）**：0.1.12 用 `textOf(event)` 扫全部事件，`/批次|batch/i` 命中工具结果里的 JSON 字段 `"batch"` 也会生成标记；取不到 `a/b` 时 `ratios=[]`，而旧 `ratiosCovered([])` 只要求摘要非空 → **空泛 pass**。0.1.13 收敛到对话正文并让 `ratios=[]` 判 `skip`，但留下两个问题：助手消息里的 `2/6`（收口计数）、`183/183`（测试数）被当批次比例 → 判 `fail` 并写 `manual-compaction-loss` 假阳性；日期 `YYYY/MM`、正文 `{511/958}` 仍会误伤。0.1.14 改为**同消息绑定**：① 批次语义与比例必须在同一条消息正文里（跨消息拼凑不算），否则 `skip(no-batch-semantics)`；② `YYYY/MM`（19xx/20xx + 1–12）不算比例，只剩日期时 `skip(date-like-ratio)`；③ `stripStructuredPayload` 只剥“像 JSON 的”`{…}`/`[…]`（含引号或冒号），正文 `{511/958}` 保留。**判据原则：宁可 `skip` 不可 `fail`**——`fail` 会触发 `manual-compaction-loss`，误报代价高于漏报；真实批次进度必然带“批次/进度”字样，漏报概率低、后果轻。真值样本：`0.1.12 seq=11479 ratios=[] → pass`、`0.1.13 seq=11453 ratios=["2/6"] → fail`，0.1.14 两例均 `skip(no-batch-semantics)`（`analysis/req-20261025-05/`）。

报告只保留 seq/类型/字符数/状态，不含消息正文或路径（有测试断言）。每次报告最多保留 20 条，供 T5 审计与 `/cg status` 读取。

### 4.2 压缩前后时点

```
compaction/start   → snapshotProtection(session)（只读快照）
compaction/summary → 校准摘要可读性/风格；适配器可能从 pending → pass
user/message       → 记录 compact-checkpoint 的 seq
compaction/end     → verifyProtection(..., postSurfaceNodes=session.surface.nodes)
```

插件在事务中途才挂上时，用 summary 时刻补快照并标 `lateSnapshot`；完全错过 start 的 `end` 记为 `skipped`。畸形事件只增加计数/忽略，不向宿主抛错。

## 5. 模式、冲突与降级

| 模式 | 条件 | 治理行为 |
|---|---|---|
| `full` | 已知后端 + 事件面可用 + 版本在矩阵或未知（warning） | 保护校验全开；T4 可回注 |
| `degraded-summary-unreadable` | 摘要为空/不可读 | 只放 ID+状态（T4）；批次/回滚覆盖检查 `skip` |
| `observe-only` | 无 provider / 未知 provider / 自检 fail / 版本出矩阵 / 无 `ctx.on` | 只观测与审计，不干预、不回注 |
| `disabled` | `compression.enabled=false` | 完全不订阅 |

冲突码：`no-compaction-service`、`unknown-provider`、`event-api-unavailable`、`self-check-failed`、`host-version-unverified/out-of-matrix`、`backend-version-unverified/out-of-matrix`、`summary-provider-drift`。
context-zip 自检失败时输出 `fallback: {recommended:'host-default', manual:true}`——**只给建议，不替用户换引擎**；换引擎必须人工改 profile + 重启。

## 6.4 版本矩阵放宽与 provider→事件级路线（2026-10-25，v0.1.2）

- **原因**：真实安装后宿主是 `0.2.1-rc.3`（app.asar 实测；旧 runtime 缓存仍显示 rc.2），原矩阵精确枚举 `0.2.1-rc.2` → `host-version-out-of-matrix`；日志 `adapter=none` 说明 apply 时也探测不到 `compaction` 服务。
- **v0.1.1 的错误尝试**：把 `compaction` 加进 `inject` 后插件永远 pending、apply 不执行（本机该服务对根级插件不可见/未挂载）。v0.1.2 **回退** `inject=['tools','commands']`，压缩探测改为惰性 + 显式诊断，不再把 provider 当硬依赖。
- **新路线**：provider 缺失时 `mode=event-level`（E1 已验证的 `session/event` 里的 `compaction/*`），T3 保护校验与 T4 固化/回注照常工作；apply 一定执行，并在 warn + 诊断行写明 `compaction-service=absent(token=compaction)`。
- **矩阵规则**：host 用同 rc 线区间 `>=0.2.1-rc.2 <0.2.2-0`；接受 `0.2.1-rc.2/rc.3/rc.4…` 与 `0.2.1` 稳定版；拒绝 `0.2.1-rc.1`、`0.2.2-*`、`0.1.x`。
- **backend unknown**：引擎标记识别为 context-zip 时，`backend=unknown` 只产生 `backend-version-unverified` warning，**不触发 observe-only**；已知版本出矩阵仍 fail。
- **边界**：区间只解决“版本号兼容”，不替代行为自检；provider 路线只在 `ctx.compaction` 真正可见时启用，否则永久走事件级。
- **服务 token 核查**：`@deepseek-ai/dsh-compaction` 的 `CompactionEngine` 执行 `super(ctx, "compaction")`，token 真实值为 **`compaction`**；redirect base（rc.2 副本）继承该构造器，若激活也应注册同名服务。本机根级插件拿不到它（inject 会永久 pending、`ctx.get('compaction')` 为 null），因此不采用 provider 路线；这是**可见性/挂载问题**，不是 token 拼写问题。
- **rc.3 核查**：其 `compaction-basic` 仍写 `compaction/start|summary|end`，`dsh-session` known-event-types 仍含三类事件；事件级路线不依赖 provider 可见性。运行时事件观测待重启验证。
- 测试：`compress-adapters`（rc.3/rc.4 pass、0.2.2-rc.1/0.1.9 fail、backend unknown 只 warn）、`compress-selection`（无 provider → event-level）、`compress-integration`（apply 必执行 + absent 诊断）、`t4-reinjection`（provider 不可见仍能固化/回注）。
- 关联：`src/compress/adapters.js`、`src/compress/selection.js`、`src/index.js`；插件版本 `0.1.2`。

## 6.5 `perception` 语义与事件面能力探测（2026-10-25，v0.1.3）

- **现象**：0.1.2 重启后行内是 `mode=event-level` 但 `perception=none`。原因不是“收不到事件”，而是 `perception` 直接取了 `adapter.perception`——provider 不可见时契约值就是 `none`（`adapters.js` 对 `kind=none/unknown` 固定返回 `none`），与订阅是否成功无关。
- **语义修正**：`perception` 现在表示**实际感知层级**，只有 `ctx.on('session/event')` 注册成功且 guard 已 start 才返回 `event`；否则退回契约值（`none`）。`adapter.perception` 仍是“契约声明”，保留在 `/cg status` 的 adapter 块里。
- **能力探测行**（每次 apply 一行）：`governance capability version=0.1.3 pid=… probe=on=fn,emit=fn,get=fn,events=obj(dispatch=fn),bus=absent,session=absent,…,get.sessions=absent,…,root=self`；**只记类型**（`fn`/`obj`/`string`/`absent`/`throws`），不记值、不深挖对象内容。实现 `src/capabilities.js`；测试断言不泄漏 session id / 路径。
- **订阅通道结论（源码级）**：`dsh-session` 的提交路径用 `collectSessionCallbacks(entry.emitCtx, [carrier,'session/event',session,event])` → `ctx.events.dispatch('emit', …)`；`carrier = scopeTarget(session, scopeOf(store.ctx))`（`dsh-scope`）的过滤器对**未打 scope 标签的监听者一律放行**（`tag === undefined → true`），因此根级插件的 `ctx.on('session/event')` 可收全部会话事件。宿主内同样用法的先例：`dsh-agent-instructions`（`inject=['sessionProjections','workingDirectory']`）、`dsh-compaction-basic` 都在根/服务 ctx 上用 `ctx.on('session/event')`。
- **本次未能“实测收到事件”的原因**：18:43 装载后到核查时没有发生新的压缩（工作区两个会话日志里最后一次 `compaction/start` 是 `18:41:28`，早于装载）；因此既不能证明收到、也没有证据说收不到。v0.1.3 用三处留痕来解决：能力探测行、`event-api=on|off`、`/cg status` 的 `events=N` 计数（每收到一条 `session/event` 就 +1），以及审计里的 `apply` 记录。
- **失败路径**：`ctx.on` 不存在 → `mode=observe-only`、`perception=none`、`event-api=off`，warn 带完整能力探测串，**绝不假报 event-level**；`ctx.on` 抛错 → guard 不 start、warn `registration failed`、perception 退回契约值。
- 测试：`test/perception-capabilities.test.mjs`（9 条：只记类型/不泄漏、单点抛错隔离、行格式、无订阅能力不假报、订阅抛错不崩、订阅成功计数、apply 即建审计、startup 行字段顺序）。
- 关联：`src/capabilities.js`、`src/diagnostics.js`、`src/index.js`、`src/compress/runtime.js`、`src/audit.js`；插件版本 `0.1.5`；全量 149/149。
