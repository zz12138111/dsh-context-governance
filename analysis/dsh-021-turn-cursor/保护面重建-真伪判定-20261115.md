## 2. 真需求还是假需求（用"不做会怎样"判）

**判据：不做 → 哪类规则会丢、丢了出什么可观测错。**

- **会丢的对象**：被压缩 shadow 的**规则注入快照**（`snapshotProtection` 把 `system/message` 规则收进 `rules`，`src/compress/protection.js:280`；重建分支 `:417-424`）。规则注入包括 `system-prompt`、`agent-instructions`、`skill-catalog` 等形式。
- **丢了会怎样**：模型在压缩后看不到规则 → 违反角色/AGENTS 约束、重复劳动、答非所问；P3 验收「5 类保护项 0 丢失」直接破。**是可观测、可归因的错误**，不是"感觉不好"。
- **因此：需求是真的。** 删除整套保护面重建 = 删掉真需求，**不允许**。

**但"system/message 形态的规则重建分支"要单独看**：
- 开发实测（`analysis/dsh-021-turn-cursor/ABC-修复形态.md:9-16`）：本机真实会话 `session-58a2e845`（51 MB / 68,365 事件）里 `system/message` 仅 **4 条**、全为 `source.kind=system-prompt`（node 0），且 **system head 不被压缩 shadow**（宿主 `relationships.ts:263`/`region.ts` 选区避开 `systemHead`）；`agent-instructions`/`skill-catalog` 实际以 **`user/message`** 出现，走 user 分支。
- **我未能独立复验该统计**：该会话日志是 `session.v4.jsonl.zstd` 压缩容器（非裸 zstd 帧，Node 解压报 `ZSTD_error_prefix_unknown`），只能采信开发实测，标注"未独立复验"。
- **判断**：system 分支在**当前真实数据面**没有命中对象，属**兜底能力**；丢掉它不改变当前可观测结果，但**该能力确实是收缩**。

## 3. A 形态是否满足原判据

**结论：满足当前判据，但不是"零降级"，是有界的能力收缩，必须带条件放行。**

- 原判据「5 类保护项 0 丢失」的落点是**规则注入**；当前规则注入以 `user/message` 出现 → user 分支重建仍覆盖 → **判据不破**。
- system 形态规则的"永久跳过"属**兜底能力归零**：当前无对象；未来若宿主把规则注入改成可被 shadow 的 `system/message`，A 会**静默丢规则**——所以必须靠审计把"静默"变成"可观测"。

**放行条件（缺一不可）**：
1. 跳过必须审计：`rebuild-skipped:no-open-step`（含 slot/原因），且 loss 走既有 `compaction-loss` 告警——**不允许静默**；
2. **user 分支重建保持**（规则注入主路径），C33 四态回归必须绿；
3. 新增用例：**模拟 system 规则被 shadow → 跳过不崩 + audit 出现 + user 规则仍重建**；
4. 文档（发布说明/README）写明「system 形态规则在压缩事务内不做兜底重建（无 open turn/step），跳过并审计」；
5. 若未来出现 `rebuild-skipped` 且伴随 `compaction-loss` 的 `rule-injection` → **升级处理**（C 形态延后重建或要求宿主提供合法写入窗），单独立项，**不得默默吞掉**。

**对 C33 的答复**：**C33 不加"system 兜底除外"**。C33 是"任何插件补写的 `system/message` 必须合法；推不出就跳过+审计"——A 不再写 system/message，自然满足。另加 **C34** 覆盖"规则注入重建覆盖"（见 §4）。
