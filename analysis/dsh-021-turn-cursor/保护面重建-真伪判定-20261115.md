## 3. A 形态是否满足原判据

**结论：满足当前判据，但不是"零降级"，是有界的能力收缩，必须带条件放行。**

- 原判据「5 类保护项 0 丢失」的落点是**规则注入**；当前规则注入以 `user/message` 出现 → user 分支重建仍覆盖 → **判据不破**。

**放行条件（缺一不可）**：
1. **命中即审计、零命中不刷**：`surface-rebuild-skipped`（reason=`no-open-step`）**仅在确有 system 形态规则命中 shadow 时记**（零命中不产生审计噪音），字段必须带 `sessionId/cycle/compactionId/ruleSeq/kind`（与既有 rule-injection fail 同 cycle 成对，否则"可发现"退化成各说各话）；`compaction-loss` **不单独造**，由既有 `rule-injection fail` 自然触发（`protection.js:544-555` → `runtime.js:2322-2339`）——skip 审计是"命中痕迹"，loss 是"后果告警"，两者不重复造；
2. **user 分支重建保持**（规则注入主路径），C33 四态回归必须绿；
3. 新增用例：**模拟 system 规则被 shadow → 跳过不崩 + audit 出现 + user 规则仍重建**；
4. 文档（发布说明/README）写明「system 形态规则在压缩事务内不做兜底重建（无 open turn/step），跳过并审计」；
5. 若未来出现 `surface-rebuild-skipped` 且伴随 `compaction-loss` 的 `rule-injection` → **升级处理**（C 形态延后重建或要求宿主提供合法写入窗），单独立项，**不得默默吞掉**。

- ③ **损失面分类验收（本条是放行的核心）**：
  - **a 类：可再生成** —— 宿主下一轮会重新注入的 `system-prompt` 快照。允许丢，记 `transient`，不算违规；

### 10.2 分形态立法（00 已定，入 C34）

### 10.3 对 00 第 2 问的回答（需求侧建议；多家意见已并入）
**会变噪声。** 若每次中段 shadow 都按 `rule-injection` fail 报警：`53ece2c2` 一次就有 1291 个 shadowed seq，压缩频繁的会话一天可积累几十上百条"fail"，真丢失（user 规则被 shadow）会被淹没，告警失去筛选力。故 C34 必须写 **分型 loss**。

**字段写法（审核 05:0x 修订，需求侧采纳）**——不要只写一个 `disposition`（"代码自己宣布可接受"=被告兼法官，且日后宿主不再回写 head 时历史行会撒谎）：
- `lossClass`：原始分型，`system-prompt-skip` ｜ `user-rule-loss` ｜ `b-class-loss`；
- `disposition`：**派生自 `lossClass`**（不由 skip 处直接写）；
- `dispositionRule=v1`：策略版本号，便于日后重算；
- `compaction-loss`：**只含** `unacceptable`（判据只读它，老读方按 `failures` 报警不受影响）；`compaction-loss-accepted`：汇总 count/seqs，**不逐条报警**（开发实现建议，与审核三字段兼容）；
- 白名单加 `disposition:'text'`、`acceptedCount:'number'`；`failures`/`entries` 复用现有字段；`kind` 未知 **必须默认 `unacceptable`**（保守，否则淹掉真丢失）。

**可对账（00 补充）**：`accepted` 不能只按日汇总条数，每条要能按 `compactionId` 回查到具体那次压缩（skip ↔ loss 双向关联，字段带 `sessionId/cycle/compactionId/ruleSeq`）。

**阈值（00 补充）**：写成**可调项**，不作判据硬值；审核建议用相对量——`accepted / 当日压缩次数 > 10%` 才升级人工看（固定 50/日 会被大会话误导）。

### 10.4 C34 v3 两稿（现状：**v3a 技术可行但存在争议，未冻结**）
**v3a：system-prompt 降级为 `user` 形态回注（0 丢失）**
- 前提：`user/message` 不在 `STEP_EVENT_TYPES`（`relationships.ts:8`），恢复期不要求 turn/step；编码器 `assertV4SystemMessageFields` 只查 `system/message` ⇒ compaction/end 事务内**可直接写**，无需 turn 来源，不会造半状态事件（开发 05:0x 证）。
- 内容：`rule.text` 原样、`source` 仍带 `system-prompt`，可逐字保留。
- **反对（开发）**：① 角色语义——system 内容以 user 注入 = 系统规则降级成用户输入，优先级消失，`MESSAGE_ROLE_BY_TYPE` 硬映射不允许混用；② 自证闭环——`verifyProtection` 的 `rule-injection` 用 `hasNewer`（同 kind + 更大 seq + 在 post surface）判"有更新副本"，user 副本会被判 **pass，掩盖真实缺失**；③ 装配错乱——`agent-instructions`/`skill-catalog` 在宿主装配侧有 kind 语义（排序/去重/注入位），塞进去会被当普通用户消息。⇒ 开发结论：**技术可行，但不可作为修复**。
- **支持（审核）**：v3a 比"分型 accepted"强——事故根子是"宁可丢也不崩"，v3a 是"既不丢也不崩"；只要满足三条即可：① 合法（`user/message` 不受 `requireStep` 约束，已有证据链）；② **幂等**（下一轮宿主重发 system prompt 不得重复累计——重建前查同 cycle 是否已有副本，`source.form='surface-rebuild'` 可识别）；③ **语义可辨**（不进"用户语音"语义，kind/title 保留原样）。若开发证 v3a 不可行则走 v3b。
