# D2 入口形态调查（2026-11-14）——「压缩百分比」放哪最顺手

> 背景：用户否决"只能进设置页改"：「为啥是设置页，不能直接在下面就像电脑操作或者什么地方一样搞个小框输入吗……我需要更好的用户友好型设计」。
> 方法：只读核对宿主 `app.asar` 内 `@deepseek-ai/dsh-client-ui-*` 官方 README + 本机已装第三方插件实证；未改代码。

## 0. 结论（一行）

**推荐 A：在输入框下方的统计行（`conversation.composer.dock`）放一个「压缩阈值 65%」小条目，点一下在同位置弹出 `conversation.input.overlay` 气泡，里面是百分比输入框 + 当前生效值/来源层/生效时点 + "打开设置页"。**
改动只落在 `lib/client.js`（约 +120 行手写 bundle），**宿主侧不动、打包面不变、不新增路由**。已有第三方先例：`dsh-cost-meter` 就是用这套 dock/overlay。

**与 `/cg` 命令的双向**：保持。UI 写 **plugin 层**（profile patch，`config-reload` 后立即生效）；`/cg set compact.at=0.55` 写 **session 层**（即时、重启失效）。气泡/面板显示 `source` 层，两条路径并存、不互相覆盖。

> **更正（2026-11-14，TEST-08 之后）**：本句原写"显示 `source` 层正是 C8/C11 要的"，不完整。C8 要"当前生效值 + 来源层 + **生命周期**（`source=session` → 本会话有效/重启失效；持久层 → 保存后生效、重启仍有效）"；C11 额外要"**本次修改写入哪一层**"（本实现固定 = plugin 层 / profile patch）。只显示 `source` 不等于满足 C11。

## 3. 推荐 A 的理由（按用户原话逐条对）

1. **"直接在下面…搞个小框"** → `composer.dock` 就在输入框下方那一行，和现有的"用量/速度"统计并排；用户打字时一直看得见。
2. **"像电脑操作"** → 一个可点的数值 chip + 一个气泡输入框，不是"进设置页找一页表单"。
3. **3 秒改到值** → 看到 `压 65%` → 点 → 输 `55` → 回车 = 4 步，无路由跳转。
4. **看得见当前生效值+来源层** → 气泡内三行（当前生效 / 来源层 / 生效时点），数据来自已实现的 `/context-governance/policy-snapshot` GET，不新增接口。
5. **不浪费已做的** → `settings.section`（`20bf20d`）保留为"完整设置页"（方案 C 的入口也可顺带加），不做废。

## 4. 实现面（不写代码，只列）

- **只改 `lib/client.js`**：现有 `settings.section` 注册保留；新增 `conversation.composer.dock` 条目（唯一 id，如 `context-governance.at`，order 取 2，排在 `usage` 之后）+ `conversation.input.overlay` 气泡（内部复用现有 `fetchSnapshot`/`toRatio`/`validateRatio`/`renderPolicyText` 与 `configForms.get(...).set('policy.at', ratio)`）。
- **host 侧零改动**：快照路由与 volatile 配置沿用 `20bf20d`；不需要新包、新端口、新依赖。
- **包面不变**：仍然只有 `lib/client.js` 一个浏览器文件。
- **证据/先例**：`ui-chat` 的 dock 条目（`activity`/`usage`）、`message-feedback` 的 overlay dialog（body portal）、`cost-meter` 的 dock+overlay 实际用法。
