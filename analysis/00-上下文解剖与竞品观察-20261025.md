## 3. 三个反直觉结论

1. **用户对话不是大头**：7 天用户消息 29.4 万字符（1.8%），今日 2.6 万字符。"00 直接对话导致膨胀"体感成立，但机制不是对话文本，而是"每回合被放大成 8.9 次调用"。
2. **最大乘数是串行工具调用**：今日 597 个带工具调用的 step 里，573 个只发 1 个调用；仅 17 个发 2 个。每次 step 都重读约 26 万 tokens。把独立调用并行/批量，直接按比例省，且零信息损失。
3. **压缩不是主角**：7 天只压缩 7 次，prune 22 万 tokens。压缩本身还要把整段历史喂给摘要模型，频繁早压不划算。"少进"（工具结果折叠、工具定义收敛）与"少次"（批量调用）比"压得好"更值钱。

## 4. 固定开销：91 个工具定义 ≈ 39k tokens/次

- 最大单项：pwsh 3.5k、workflow 3.4k、schedule_create 3.1k、schedule_update 2.4k、subagent 2.1k、browser_screenshot 1.6k、history_read 1.5k、app_launch 1.5k、browser_fill 1.5k。
- 长尾很大：browser/computer/schedule/im 等一批工具，00 在管理型会话里低频使用，却每次调用都携带定义。
- 按会话类型/预设做**工具白名单**，是确定性节省（预计每次 8–15k tokens），且不影响压缩与记忆。

## 5. 工具结果：已有 50k 字符/条上限

- 宿主对单条工具结果有约 49,932 字符截断（日志里多条正好卡在上限）。
- 但结果会一直留在上下文里直到压缩；3.5M 字符的唯一结果，会在后续每一步被重读。
- 可做的不是"再截短"，而是"进上下文时就折叠成 head/tail + 落盘路径"（宿主已有 `dsh-compaction-tool-result-pruner` 这类包，可直接配置或借鉴）。

## 6. DSH 生态：别人怎么解决 M-C-O

> 插件市场数据源：`api.deepseek1024.com`（13,846 插件；memory 550 条、compaction 50 条）；npm `dsh-plugin` 关键词。

### M（记忆）——主流是"小常驻 + 大按需"

| 插件/产品 | 操作逻辑 |
|---|---|
| **dsh-mnemon**（693★） | 三层：Runtime（每轮常驻 USER.md/MEMORY.md）＋ Project Documents（先搜后读）＋ Memory Spaces（按需召回）；Sources + Strategies + Core 合成每轮 View；Budget 明确；每轮显示"读了/写了什么"（turn memory bar）；Provider 可插拔（Mem0/OpenViking/Honcho…）。 |
| **meow-memory**（跨会话） | 七层 SQLite（soul/user/project/fact/lesson/topic/rules）；首轮注入长期快照；第 2 条消息起按关键词命中 top-2（全局+项目锚）；静态 guide 放 system prompt 保 cache；压缩后自动重注入；≥7 步触发 reflection；空闲 ≥3h 低峰 dream  consolidation；8 个 memory 工具。 |
| **memory-eternal** | 对话结束自动沉淀知识卡到 Markdown Vault（可 git 管理）；CJK 检索；`memory_recall` 按需召回；零人工。 |
| **Hindsight / MemOS / OpenViking** | 长期记忆 + 自动 recall/retain + 知识页/图；按仓库或任务隔离；强调"省 token 的召回"而非全量注入。 |
| **graph-memory** | 抽取三元组建知识图谱，声称压缩上下文 75%，跨会话复用。 |
| **Claude Code（参照）** | CLAUDE.md（常驻指令）＋ auto memory：`MEMORY.md` 索引只加载前 200 行/25KB，主题文件按需读；压缩后重新注入 CLAUDE.md、auto memory、最多 5 个最近文件；`/context` 看分类占用；`/compact focus` 指定保留；`/autocompact N` 调阈值。 |

**共同逻辑**：常驻的必须极小（索引/快照/规则），细节检索读取；写入有 schema/去重；压缩后要主动重注入，否则"失忆"。

### C（压缩）——三条路线：质量、控制、零 LLM

| 插件 | 操作逻辑 |
|---|---|
| **dsh-context-zip**（现用） | 替换 compaction-basic 引擎；五段式 handoff；segment 目录；notes 注入下一次摘要；history_segments/read/search 回读。 |
| **dsh-compact-relay** | 容量监控 + **压缩预览确认** + 九段式交接单 + 消息锁定（pinned）。把压缩从"黑盒"变成"可预演的交接"。 |
| **billion-context-dsh / ACP 系** | 模型决定何时/压缩什么；提供 compress/decompress/search_context/acp_status 工具；CompactionEngine 后端。 |
| **dsh-compaction-instant / dsh-argp** | **零 LLM** 的确定性压缩（引用图剪枝/选择性遗忘），压缩率可精确兑现；不重写历史。 |
| **dsh-compact-suite / threshold / saviour** | 调阈值、面板一键压缩、摘要换指定模型、让引擎读数对齐卡片。 |
| **dsh-compact（遥测）** | 记录每次压缩的 shadowed tokens、摘要成本、模型；`/compact-stats`。 |
| **dsh-session-handoff / compact-and-branch** | 压缩后开新会话，用结构化交接单续接。 |

**共同逻辑**：压缩已是红海；差异化在"可控（预览/确认/焦点）"与"可逆（回读/零 LLM 剪枝）"。

### O（可观测）——已有但分散

- **dsh-context**（3,535★）：上下文洞察面板，构成占比、按请求历史、压缩/注入事件、消息级 token。
- **dsh-compact**：压缩遥测；**dsh-token-optimizer**：输出阶梯、MCP 懒加载、压缩驱动、cache 命中报告。
- **成本侧**：dsh-cost-meter / dsh-usage / bottom-info-bar。

**缺口**：能回答"这一回合为什么贵、贵在哪一步、下一步怎么省"的**可执行观测**，没有。

## 7. 市场空白与我们的位置

- 记忆插件多，但多数记"事实/偏好"，不记**任务状态**（open loops、验收标准、依赖、当前步骤）。
- 压缩插件多，但都在优化"压缩后的摘要"，很少优化**压缩前的进入量**（工具定义、工具结果、串行 step）。
- 观测插件有，但停在"显示占用"，没有"按类目归因 + 可执行建议 + 预算闸门"。
- 因此我们的差异化不应是"再做一个记忆/压缩插件"，而是 **M-C-O 之上的管理型会话上下文治理**：
  - M：任务态记忆（不只是事实）＋ 记忆头 + 索引；
  - C：策略与适配层（可换引擎）＋ **进入量控制**（工具白名单、结果折叠）；
  - O：每轮/每步归因（context / steps / tool mix / cost）＋ 预算告警；
  - 新增一条横切：**执行经济性**（批量/并行工具调用，减少 step 数）。

## 9. 压缩策略光谱（扩展参考面）

> billion-context（ACP）值得单独拆：它把"压缩"从"到阈值自动摘要"改成"模型用工具主动写检查点"。核心机制见 <https://github.com/Tyan66666/billion-context-dsh>、内核 <https://github.com/ranxianglei/acp-kernel>。

| 策略 | 机制 | 代表 | 省 token | 信息损失 | 压缩成本 | 可控/可逆 | 适配 00 |
|---|---|---|---|---|---|---|---|
| 交接摘要 | 范围→结构化摘要，原文留档 | context-zip、Claude `/compact`、compact-relay 九段 | 高 | 中高 | 高（一次 LLM 读全文） | 中 / 可回读 | 阶段切换、收尾 |
| 模型自写检查点（ACP） | 模型用 `compress` 写摘要；nudge 只建议；`decompress/search_context` 可逆 | billion-context | 高 | 中（依赖模型判断） | 低（无第二次摘要调用） | 高 / 可逆 | 长任务连续推进 |
| 确定性剪枝 | 引用图/规则删中间段，零 LLM | argp、compaction-instant、宿主 tool-result pruner | 中高 | 低（只删可重建） | 零 | 高 / 可回读 | 工具结果与重复内容 |
| 工具结果清理 | 到阈值清旧 tool_use/result，保留对话 | Anthropic context editing、tokenGuard | 高 | 中（细节丢失） | 零 | 中 / 原文在日志 | 最直接（工具结果 3.5M） |
| 递归/分层摘要 | 摘要再摘要（T2/T3） | ACP tiers、MemGPT 系 | 高 | 高（累积损失） | 中 | 中 | 超长会话兜底 |
| 检索式历史 | 不压，建索引按需搜 | history_search、search_context、memsearch | 中（省峰值） | 零 | 低 | 高 | "找得到"而非"记得住" |
| 结构化记忆抽取 | 抽事实/决策入库 | Mem0、Claude auto memory、meow-memory | 高 | 中（抽取偏差） | 中 | 高 | 跨会话 |
| 会话分支/交接 | 新会话 + 交接单 | compact-and-branch、session-handoff | 高 | 中 | 低 | 高 | 阶段切换 |
| 缓存感知 | 前缀不变 / append-only / 静态段落 | Claude prompt caching、meow 静态 guide | 中（省钱不省 token） | 零 | 零 | 高 | 所有策略的前提 |
| 子代理隔离 | 大读放子上下文，只回摘要 | Claude Code subagents、DSH subagent | 高 | 低 | 中 | 高 | 00 已在用 |
| 状态对象外置 | 计划/待办/验收标准落文件，不靠历史 | `todo_write`、plan 文件 | 中 | 零 | 零 | 高 | 管理型会话 |
| Token 级压缩 | 删词/缩写/丢弃虚词 | LLMLingua 等 | 高 | 高（工具名/路径易坏） | 低 | 低 | 不推荐 |

**ACP 的六个可借鉴设计**：
1. 模型自写摘要，省掉"再喂一整遍历史给摘要模型"的那次调用；
2. 只 nudge、不强令，模型决定何时压、压哪段；只有上下文超窗才自动抢救；
3. 可逆：原文留在 append-only 日志，`decompress`/`search_context` 随时找回；
4. 保护规则：最新用户消息、注入的 AGENTS.md/skill 目录副本、tool-call/result 配对边界——避免"压了又重注"的死循环；
5. 记账用宿主 token-meter，不混用插件自估；预算扣除输出预留；
6. 五档 preset + 运行时热调 + 每个 realm 只留一个压缩后端。

**对我们的含义**：不要选"一个压缩算法"，而要定"策略组合 + 保护规则 + 引擎适配 + 观测"。对 00，优先级大致是：工具结果清理/折叠 > 确定性剪枝 > 状态对象外置 > ACP 式模型自写检查点 > 交接摘要 > 分层摘要。
