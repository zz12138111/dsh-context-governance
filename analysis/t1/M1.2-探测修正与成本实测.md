## 2. 代码改动

### 2.1 能力探测双行

- `src/capabilities.js`：`SELF_PROBES`/`SERVICE_PROBES` 增加 `tokenMeter`。
- `src/diagnostics.js`：`capabilityLine(entries, phase)` → `capability@apply` / `capability@ready`（诊断日志）。
- `src/audit.js`：新增 `capability@apply` / `capability@ready` 事件；白名单新增 `probe: 'text-array'`（只记 `name=类型`，不记值）。
- `src/index.js`：
  - apply 时写 `capability@apply`（诊断 + audit）；
  - 构造 `CompressionGuard` 时传 `onFirstEvent: probeReadyCapability`；
  - 首个 `session/event` 后写 `capability@ready`（诊断 + audit + logger 行 `capability@ready compaction=... tokenMeter=...`）。
- 关键点：**apply 行保留**（历史对照），不把 apply 的 absent 改写；ready 行给出真实可用性。

### 2.2 tokenMeter 延迟获取

- `CompressionGuard` 构造时只试探一次，**失败不缓存 null**。
- `#getTokenMeter()`：每次按需 `ctx.tokenMeter ?? ctx.get('tokenMeter')`；只有拿到 `measure` 函数才缓存。
- `#tryInjectTokenMeter()`：`ctx.inject(['tokenMeter'], scope => ...)` 可选注入；服务就绪回调写入 `#tokenMeter`，dispose 存 `#meterDispose`，`stop()` 清理。
- **没有**把 `tokenMeter` 加进 `export const inject = ['tools']`；缺服务不会让插件 inactive。

### 2.3 usage 兜底与来源

- 新增 `#lastUsage`（按 session 缓存最后一条 `assistant/message` usage）与 `#pendingCosts`（等 after usage 的成本行）。
- `#usageOf()`：只取 `inputTokens + cacheReadTokens + cacheWriteTokens`；至少一个有限数值才算有 usage；`usage={}`/无字段 → 不算。
- `#newCost()`：
  - `tokenMeter` 可用 → `tokensBefore=measure(session)`，`tokensBeforeSource='tokenMeter'`；
  - 否则最后 usage → `usage`，并记 `tokensBeforeParts`；
  - 都没有 → `null` + `none`。
- `#writeCost()`：
  - end 后回注 microtask 后测 meter；可用 → `tokensAfter` + `tokenMeter`；
  - 不可用 → 挂 `#pendingCosts`，等 end 后第一条 `assistant/message`；
  - 等不到（stop/新周期开始）→ `null` + `none`（`#flushPendingCosts`），不静默丢。
- 审计新增 `tokensBeforeSource`/`tokensAfterSource`/`tokensBeforeParts`/`tokensAfterParts`，`auditVersion='cost-v1.1'`；**旧字段名与语义不变**。

### 2.4 `/cg status`

新增 `last-cost:` 行（`guard.status.lastCost`）：

```text
last-cost: before=1400(tokenMeter) after=500(tokenMeter) trigger=auto
```

未写入时 `last-cost: none`。

## 5. `ctx.compaction` 可用性结论

**结论：可获取（ready 时）。** apply 时 `absent` 是探测时机，不是宿主不支持。

证据：
- `dsh-base/cordis.patch.yml:348-352` 默认挂 `token-meter` + `compaction-basic`；
- `@deepseek-ai/dsh-compaction` 定义 `ctx.compaction` 服务（`dsh-compaction/lib`）；
- 本机 profile `~/.dsh/profiles/desktop/cordis.patch.yml` 有 `compaction-basic.thresholdRatio: 0.65`；
- 真机会话 `58a2e845` 有真实 `compaction/start(seq 4193) → summary(4195) → end(4197)` 和手动 `8535→8537→8539`；
- 新增 `capability@ready` 会在首个会话事件后给出 `ctx.compaction`/`ctx.get('compaction')` 的真实类型。

**仍待真机确认**：用户重启后看 `logs/governance.log` 的 `capability@ready ... compaction=... get.compaction=...` 与 `audit.jsonl` 的 `capability@ready` 行。本单不改压缩后端、不替换 provider；provider 可得后“回注时点”是否可修，留给 M2/P1 决策。
