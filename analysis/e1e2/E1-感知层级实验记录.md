## 3. 逐层结论

### 3.1 事件级：可用（两后端一致）

压缩事务固定写四个持久事件（同一秒内、顺序固定）：

| seq 相对位置 | 事件 | 关键字段 | 源码 |
|---|---|---|---|
| +0 | `compaction/start` | `compactionId`、`turn`、可选 `sourceCommandId` | `dsh-compaction-basic/lib/index.js:469` |
| +1… | 摘要 LLM 调用（`ctx.llm.stream`，复用会话前缀吃 cache） | — | `:899`、`:582` |
| +N | `compaction/summary` | `summary`（纯文本）、`rawOutput`、`shadowedRange`、`shadowedSeqs`、`shadowedTokenCount`、`provider`、`model`、`usage` | `:634` |
| +N+1 | `user/message`（compact checkpoint） | `source.kind="compact-checkpoint"`、`source.compactionId`；`surfaceOp={op:"replace",startSeq,endSeq}`；`sourceEventSeqs=[start,summary,…shadowed]` | `:650`；`dsh-compaction/lib/index.js:109-130` |
| +N+2 | `compaction/end` | 成功无额外字段；失败带 `error` 链 | `:484`、`:495` |

**观察入口**：`ctx.on('session/event', (session, event) => …)`——宿主自己的持久化插件就用这行（`dsh-session-persistence-jsonl/lib/index.js:421`）；事件在 `Session.commit()` 里同步派发（`dsh-session/lib/index.js:1585-1592`）。
**时机**：`compaction/start` 先 append、后进入 `summarizeCompaction()`，因此监听者在**摘要调用之前**收到通知；但此时事件里只有 `compactionId/turn`，**看不到将被压缩的范围**（范围在 summary 事件里）。
**实测**：16 次压缩全部有完整 `start → summary → checkpoint → end`；0 次 `compaction/end.error`；10 个会话命中。

> 结论：事件级成立；M1 最低要求的“状态级”被超过。治理层可以在 `start` 时“确认固化已发生”，在 `summary/end` 时读摘要、比覆盖、写审计。

### 3.2 工具级：可用

- 手动压缩命令 `/compact`：`dsh-command-compact/lib/index.js:49-99`，走 `ctx.compaction.compactNow()`，产出 `command/run` → `command/done` 事件。
- context-zip 额外提供 `/zip-compact`（manual seat，见引擎 `addManualCompactionSeat`）与 `/zip-export`、`history_*` 检索工具。
- 实测手压 10 次（多数来自 context-zip 的 `/zip-compact`），自动 6 次；输出示例：`Compacted 1930 event(s) (~497298 tokens) … summary event #20939`。

### 3.3 状态级：可用（作为补充）

- `ctx.tokenMeter.measure(session)` 给出按 surface 节点的 token 计量；压缩前用它判断阈值（`compactIfNeeded`，`:914-946`）。
- `compaction/summary.shadowedTokenCount` 与 `usage`（input/output/cacheRead/cacheWrite/total）都可读：16/16 有 usage。
- 代价：`usage` 是**摘要调用**的用量，不是“省下的 token”；16 次里 `totalTokens` 从 22,960（短会话）到 565,011（长会话），长会话那几次 `cacheReadTokens` 占大头（输入侧实际约 50 万–59 万 token/次）。成本归属必须把它与 shadowed 数分开记（E5 再定口径）。

## 4. 感知的边界（写进适配器契约的部分）

| 问题 | 答案 |
|---|---|
| 能否知道“压缩即将发生”？ | 能，`compaction/start` 在摘要调用前同步到达；但只知道 compactionId/turn，不知道范围。 |
| 能否阻止/改写本次压缩？ | **不能**。宿主没有 pre-compaction waterfall；能拦住压缩的只有“替换 `ctx.compaction` 实现”（那会与 context-zip 抢行，M1 不做）。 |
| 能否在压缩前注入内容让它进入摘要？ | 不建议：摘要输入在 start 之后由 `shadowedSeqs` 固定构造（`prepareCompaction`），且 `append` 在发布期间禁止重入。固化必须**提前持续发生**。 |
| 能否拿到被压缩范围与原文？ | summary 事件给 `shadowedRange/shadowedSeqs`；原文仍在 append-only 日志里，可按 seq 回读。 |
| 工具配对谁维护？ | 宿主。选择范围时要求 `toolPairingBalancedBefore`；提交前 `validateSurfaceRegion` 再断言；治理层只做校验/审计。 |
| 摘要可读吗？ | 两后端都可读：`compaction/summary.summary` 是纯文本。宿主默认自由摘要 6 次（2.3k–11.6k 字符）；context-zip 五段式 10 次（3.1k–5.0k 字符，10/10 命中 5 个标题）。 |
| 失败能感知吗？ | 能：`compaction/end` 带 error；另有 `compaction/summary-error` waterfall 供恢复提供者使用（`:1017`）。 |
| 版本漂移怎么防？ | 冷启动只读探测：`ctx.compaction` 是否存在；初始化后能否观察到 `compaction/start|summary|end`；summary 是否可读；五段式是否可识别；redirect 包版本（context-zip 形态）。 |

## 5. 两个后端的差异（E1 直接产出）

| 维度 | 宿主 `compaction-basic` 0.2.1-rc.2 | context-zip 0.1.10（接管该行） |
|---|---|---|
| 控制权 | 宿主压力 + 手动 `/compact` | 同左（手动另有 `/zip-compact`） |
| 感知层级 | **事件级（已验证）** | **事件级（已验证）** |
| 触发面 | `session/event` 的 compaction/*；命令 | 同左；只覆写 `summarize()`（`engine.js:856-958`），事务/事件全部继承宿主 |
| 前/后钩子 | 无拦截型前钩子；start=摘要前通知；end=提交后通知；`summary-error` waterfall 仅失败恢复 | 同左 |
| 摘要权威 | 独占（整段替换为 1 个 checkpoint） | 独占；五段式 handoff |
| 摘要可读性 | 可读（自由文本） | 可读（固定 5 段；可判结构） |
| 改写边界 | `surfaceOp.replace` 替换 span；工具配对由宿主维护 | 同左 |
| 保护角色 | 宿主=执行者；治理层=校验者/观察者 | 同左 |
| 可观测性 | provider/model/usage/shadowedRange/Seqs/TokenCount 全在 summary 事件 | 同左；另有历史检索工具与工作笔记 |
| 契约自检建议 | 事件可订阅 + summary 非空 + endpoint 一致 | 五段标题命中 ≥4 + redirect 版本/base.json |

**回写建议**：`docs/上下文治理插件-架构说明-v1.0.md` §6.3 两张表的“事件级（待验证）/可读（待验证）/待验证”可按下表替换（完整可粘贴版本见 `analysis/e1e2/行为矩阵-6.3回写字段.md`）。ACP 三行保持“未安装/未验证”，M1 不接。

## 6. 风险与未验证项

1. **没有运行时插件探针**：事件订阅结论来自“宿主源码 + 第一方插件用法 + 持久化日志”，不是“我们自己的插件跑起来收到了事件”。这是红线约束下的证据上限；T3 首装时应补一次 5 分钟探针（只读日志 + `/cg status`），见 T3 验收。
2. **事件级 ≠ 可干预**：M1 的“压缩保护”只能是压缩前断言 + 压缩后核对，不能阻止宿主压缩；这与架构 §6.6 一致。
3. **范围在 summary 才可见**：`start` 事件不含 range，若审计要求“开始即记 range”，只能用 tokenMeter 复算（与宿主选择算法同口径），本实验未做。
4. **版本漂移**：宿主升级可能改事件字段/时机；T3 适配器必须做契约自检并在失败时降级（§6.7）。
5. **ACP**：未安装、未验证；按门禁保持“只读/不接”。
6. **context-zip 的接管形态**：依赖 profile 内 `@deepseek-ai/dsh-compaction-basic` redirect 包（版本字符串 `0.1.0-context-zip`）；插件升级/DSH 升级后 redirect 可能落后，README 也提示需重跑安装。治理层不能假设它永远存在。
